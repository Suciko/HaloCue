# HaloCue 1.0 Beta 4 · Electron 本地预览

本次候选把默认桌面入口改为真正的 Electron 44.5.1 窗口，沿用现有写作、AA 制作和 MCP 服务。最小化、最大化/还原、关闭由 Windows 原生控件提供，与工作台上栏合并。空白上栏可拖动，交互控件不参与拖动；窗口位置和大小保存到用户目录。

图标使用维护者重新选定的最初版本：蓝底、倾斜白环、青色尾笔。主程序、启动页、应用内品牌和 favicon 使用同一 SVG 生成。

打开时先显示独立启动页，再恢复作品。页面读取能力信息和作品列表并行执行；待发送反馈在页面打开后同步，不再阻塞编辑器。用户目录的 `electron/startup.json` 分别记录窗口显示、后台就绪、页面加载和工作台就绪的耗时。实测结果和条件以本次 handoff 为准。

启动页、窗口背景和原生窗口按钮跟随应用保存的深色/浅色选择；“跟随系统”按当前系统主题打开。外观缓存也用于端口被占用后的新地址，避免主题突然恢复默认。正常窗口及 960 像素宽窗口已检查上栏拖动区域、按钮空间和首页布局。

2026-10-04 R2 修正版进一步统一网页恢复期间的加载遮罩，去掉旧“HC”占位，使用与 Electron 启动页相同的图标、文案和布局；修正夜间主题覆盖及旧浅色底色缓存。恢复数据仍需要短暂加载，加载状态会连续显示。应用版本仍为 Beta 4，R2 单独交付并使用新的校验值，旧包保留。

完整解压 `HaloCue-1.0.0-beta.4-windows-x64.zip` 后运行根目录 `HaloCue.exe`。默认窗口不要求系统 Python 或 WebView2。`HaloCueBackend.exe`、`HaloCueMCP.exe` 和 `_internal` 是随包服务与运行库，不应单独移动。默认用户数据仍为 `%LOCALAPPDATA%\HaloCue`，已有作品无需迁移；不要删除用户目录。`--legacy-ui` 保留旧界面兼容入口。

保留 Beta 3 的 Codex 订阅、正文直接编辑、AA 演出提案、Codex CLI/Claude Code 配置导出。外部 Agent 修改仍先生成待决定提案；只有用户采纳才写入正式稿。Claude Code 的实际模型验收仍取决于官方客户端登录状态。

这是本地预览候选，没有合并 main、创建 tag 或发布 GitHub Release。旧 Beta 3 包保留。测试与成品校验记录见 [本次交接](../handoffs/2026-10-03-1.0-electron-icon.md)。
# R3 portable startup correction

The collaborator reported `IndexError: 5` when the frozen backend starts from a
shallow installation directory. Source-only parent indexing was still evaluated
despite a valid bundled resource root. The writing/production model adapters and
catalog locator now use the central resource-root boundary. R3 requires rebuilt
backend binaries and additional shallow-path, renamed-folder, unrelated-working-
directory and fresh-LocalAppData acceptance. It retains the original icon and
unified themed startup from R2. Final receipt: see the
[portable-startup handoff](../handoffs/2026-10-04-1.0-portable-startup.md).

## R4 work-dialog and choice correction

The new-work modal uses theme-matched controls and a separate scrolling field
area, keeping its actions and bottom spacing visible. Agent choices float above
the composer with selection feedback and a persistent send action. Custom
answers use one directly editable reply field; failed sends preserve the text
for retry. The existing audited decision-response and human approval boundaries
are unchanged. See the [UI handoff](../handoffs/2026-10-04-1.0-choice-ui.md)
for browser and package acceptance.
