## 二、用户已经明确的不可违背约束

1. 不设置硬字符预算。
2. 后端不能擅自把模型最大输出 token 改小；按用户和模型配置使用。
3. 不设置固定动作数、气泡数、特写数、镜头数、Wait 数、无对白节点数或固定镜头长度配额。
4. 每镜最多三名可见人物，绝不允许四人同镜。单人和双人是默认，三人只用于确实成立的共同反应或稳定三方互动。
5. Wait 只允许出现在无对话框节点；有对白框的正常台词节点不加 Wait。
6. 无对话框节点不是“空白占位”。它必须具有可读的表情、动作、气泡、声音、构图变化、操作反馈、心理变化或时间推进目的。
7. 普通镜头切换不等于人物真实入场或退场。`enter/exit` 只用于确实进入或离开叙事空间。
8. 硬切是官方常用镜头语法，不能为了减少切镜而压制硬切。需要避免的是按每个说话人机械反打，以及看起来像原地替换图层的假切镜。
9. 单人通常使用中央构图；双人和三人必须结合立绘真实宽度与几何标注防止重叠，不能只按固定槽位盲排。
10. 关系距离只判断当前画面中真正互动的人，通常主要用于双人镜头；不要判断画外无关人物的亲密、普通或疏离关系。
11. 表情、动作、气泡和镜头必须共同服务当前演出目的。可以组合多个表现层承载同一个爆点，不能因为抽象的“克制”而漏掉必要演出。
12. 爱丽丝日常状态不能使用凯伊人格占据身体时的红眼、黑化或身份污染差分。所有角色的特殊身份差分都必须经过硬过滤。
13. 不要关机。

## 三、用户反复观察到的实际失败

### 1. 表情与无对白节点

- 无对白节点写成 `角色(00):`，使上一拍正确表情突然归零，并在默认脸上停留约 0.65 秒。
- 角色从沉默转为说话、从听者转为回应者、从认真追问转为灵光推断时，face 长时间不变化。
- 连续两句明明发生了明显情绪升级，却重复相同或近似 face；真正峰值没有可读差异。
- 表情阶段顺序反转，例如“狼狈寻找”被选成真怒，“委屈爆发”反而使用普通认真脸；“认真追问”与“灵光推断”使用了相反强度的表情。
- 爱丽丝过度使用 `00/02`，没有优先选择更符合日常活力、认真或兴奋状态的候选；特殊红眼身份差分曾被错误选中。
- 表情符号、动作和 face 各自孤立选择，没有形成“察觉 -> 处理 -> 爆发 -> 回落”的连续反应阶段。

### 2. 强情绪与镜头重点

- 强烈台词仍保留双人或三人构图，主体没有单人居中、放大、动作或气泡。
- 安静询问、礼貌回应、普通省略号反而误用 FocusLine；真正的宣言、推断、决定和情绪爆发没有重点。
- 连续强句经常在前一句提前用掉特写和重效果，后一句真正完成升级时反而回到普通镜头。
- 但“峰值一定在后一句”也不能成为硬规则；后一句可能是余波、解释或回落，必须理解语义后判断。
- 目前提示词中“特写稀少”“保持镜头优先”“连续强句峰值后置”等措辞可能形成过度保守偏置，需要重新评估。

### 3. 多人镜头与空间连续性

- 常见错误为 `[A,B] -> [A,C]`：A 的槽位、缩放和画面关系完全不变，只把 B 的图层瞬间替换成 C。
- 切镜后新人突然冒出来，旧镜头中一人仍原位不动，观众看不到完整新构图，也没有合理的 reveal、move、reframe 或硬切重建。
- 本应是单人接力的评价台词，被拍成沉默者一直留在旁边的双人镜头。
- 多人场景一开始就把所有人摆齐，丢掉“单人建立 -> 双人接入 -> 三人共同反应 -> 单人承接”的层次。
- 为了修槽位而使用没有剧情依据的移动；或把普通切镜误标成真实入场。
- 所有人从同一侧入场，不考虑目标槽位、人物来源和画面方向。

需要特别注意：`@camera_cut` 在编译器中会清掉上一镜槽位状态并重建完整构图，因此硬切本身不是错误。但如果重建后共同人物仍处于同一槽位、同一缩放、同一关系，而另一人被替换，最终视觉仍可能像图层替换。源文本检查与编译后画面状态检查必须区分。

### 4. 无对话框反应、动作与表情符号

- 计划包含无对白节点，但节点只有 Wait，没有动作、气泡、换脸、声音或构图目的。
- 共同刺激后缺少“被刺激小组共同反应 -> 最重要回应者单人承接”。
- 物件操作直接从“尝试”跳到“成功结论”，没有操作、反馈、复核过程。
- 邀请或重大决定直接从提议跳到接受，没有吃惊、犹豫、换脸和决定余波。
- 游戏过程只使用一次按钮声，无法表达时间推进和蒙太奇。
- 空镜、沉默、点点点本可使用表情符号或动作承载心理变化，却经常什么都没有。
- 动作曾被旧密度或冷却逻辑删除；也曾因为提示词过度强调克制而根本没有生成。

### 5. 节奏与镜头语言

- 不能简单追求更少切镜，也不能简单追求更多硬切。
- 同一互动轴仍在推进时，可以 hold/reframe；刺激、承受者、完整拍摄小组、揭晓、爆点或单人余波改变时，硬切往往是正确选择。
- 不能被目前任何固定节奏、镜头长度、动作密度或官方单段统计限制。应该学习因果结构，而不是复制数量。
- 活动剧情、主线剧情、羁绊剧情可能在一个物理场景中混合出现，策略应按当前事件拍点激活，而不是强制整场只用一种模板。

## 四、已经验证的代码事实与实验结果

请先理解这些事实，再提出方案：

1. 正式后端已经存在场景事件规划器：
   `annotation_scene_planner.py`。
2. 但 `annotation_agent.py::run_annotation_agent` 的 `scene_event_planning` 默认是 `False`，正式 `annotate.py` 调用时没有启用它。
3. `annotation_scene_planner.py::event_plan_fulfillment_errors` 已经能检查计划要求的 silent phase 是否兑现，但目前没有接入生产调用。
4. 当前 `pure_ai` 路径只调用 `dedupe_exact_beats`，没有经过完整的 `normalize_direction_plan`；这与“纯 AI 也必须受后端限制和优化”的目标不一致。
5. 两阶段实验的第二步由 Agent 直接手写 AA 标注文本，绕开了正式 `annotate.py / director_policy.py` 的归一化，所以正式后端已有保护没有生效。
6. `script2aap.py` 已经区分叙事空间中的 `present` 与当前镜头可见角色，并且 `@camera_cut` 会重建槽位；这个基础不应推倒重写，但需要编译后质量检查。
7. 当前语义表情后端已经会：从数据库生成目标行 shortlist、过滤身份污染和近重复候选、向 AI 暴露 `[Emo:语义]` token，再由后端解析为真实 face id。
8. 当前提示词已经包含端到端合成演出示例、活动/主线/羁绊策略、镜头组、无对白反应、物件操作和表情阶段规则，但规则很多，且有相互牵制和过度保守的风险。

两阶段 v1 的确定性质量检查结果：

- 56 条对白，第一阶段却生成 56 个 `shot_steps`，几乎逐句规划镜头；
- 15 个 `impact_lines`；
- 0 个 `performance_beats`；
- 计划层发现 4 个双人原位换人、15 个非单人近景爆点、13 个爆点缺少动作/气泡意图；
- 源码层发现 5 个默认脸空节点、5 个多人特写、4 个原位图层替换；
- 它通过了旧的“台词一致、Wait 合法、最多三人、可编译”检查，却在实际演出上明显不合格。

已有通用结构质量检查对比：

- 参考官方研究后制作的 V4：0 个结构问题，PASS；
- 严格盲测 v1：3 个原位换人问题；
- 严格盲测 v2：8 个原位换人、2 个默认脸空节点；
- 两阶段 v1：14 个源码级结构问题。

这说明质量门有区分能力，但目前仍只是实验模块，且尚未覆盖计划到执行的逐项兑现、编译后实际槽位变化和表情阶段差异。

## 五、可供评审的当前候选方案

下面只是待评审方案，不是必须接受的答案。

### 方案概述

```text
完整场景预审
    -> 第一阶段 AI：事件链、互动轴、镜头组、反应阶段、爆点与释放点
    -> 第二阶段 AI：具体镜头执行、表情语义、动作、气泡、声音和无对白 beat
    -> 后端状态编译：人物在场状态、可见名单、槽位、缩放、资源与效果生命周期
    -> 分层质量门
    -> 只返修失败的事件或场景块
    -> 编译 AAP
    -> 编译后状态与几何复核
```

### 第一阶段不再逐句指定镜头

第一阶段只输出“最小充分导演计划”，例如：

- 事件范围、刺激、结果和当前互动轴；
- 参与者、共同反应者、主要承接者；
- 少量真正发生变化的 shot group，而不是每句一个 shot step；
- 必须兑现的 phase：cue、group reaction、focus handoff、object action、result、decision pause、montage、aftershock；
- face arc 的语义阶段与改变原因，不选择具体编号；
- 动作、气泡、声音和特写的叙事意图，不选择具体资源；
- 真正爆点的主体、建立点、峰值点和释放点。

不为事件数量、镜头数量或节点数量设配额。

### 第二阶段输出规范化演出 IR，而不是直接手写 AAP

第二阶段只接收：

- 当前事件切片及必要前后文；
- 第一阶段相关计划；
- 当前人物在场、镜头组、槽位、表情和效果状态；
- 当前角色与装束的少量 face shortlist；
- 当前事件需要的动作、气泡、声音、背景候选；
- 相关剧情模式和一小段合成示例。

它输出规范化 IR，由正式后端转换成 AA 指令。固定规则和资源表使用 prompt cache，不在每次请求中重复展开。不要靠硬字符预算省 token，而应靠检索、状态摘要、候选 shortlist、按事件分块和局部返修节省 token。

### 所有模式共享后端安全内核

建议把原“纯 AI”改名为“AI 导演”，因为不存在不受后端限制的模式：

- `AI 导演`：AI 决定镜头、节奏、具体槽位与演出，后端校验、确定性修复，并对创作矛盾触发局部返修。
- `AI 辅助`：AI 决定事件、镜头组、焦点和演出意图，后端负责具体槽位、几何和连续性优化。
- `稳定后端`：AI 主要负责语义重点和表情，确定性后端承担更多镜头与站位安排。

三种模式都必须共享：资源白名单、身份过滤、最多三人、说话者可见、Wait 合法性、人物在场状态、槽位几何、效果生命周期、硬切完整重建和质量报告。

### 后端修复分级

1. 可以确定性直接修复：
   - 无对白 `face=00` 占位改为继承；
   - 非法或身份污染资源拦截；
   - 槽位越界、重复和几何重叠；
   - reveal/enter 方向与目标槽位矛盾；
   - 一次性效果没有释放；
   - 完全重复的命令或 beat。
2. 不应机械猜测，应退回 AI 局部返修：
   - 多人镜头是否应该改成单人爆点；
   - `[A,B] -> [A,C]` 应该硬切、先收单人、移动还是 reveal；
   - 哪一句是真正峰值；
   - 缺失的共同反应、物件操作、决定停顿或余波如何表现；
   - 表情阶段倒置或同一 face 没有可读变化。
3. 后端不得使用固定数量配额替代导演判断。

### F. 质量门与返修

每条质量问题需要标明：

质量门只能检查结构矛盾和正文已有事件是否漏掉，不得通过固定镜头数、动作数、气泡数或官方统计配额判定好坏。
