# HaloCue v0.9 Beta Public and Private Release Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Publish a clean `Suciko/HaloCue` source repository and a self-contained Windows x64 public release for `0.9.0-beta.1`, while producing a separate local-only private package that can add an explicitly authorized Spine installation without ever including personal skeletons or other user assets.

**Architecture:** Separate immutable application resources from writable per-user state. Build a deterministic, sanitized annotation database; export public source through an explicit manifest; scan both source and binaries before release; package the application as a PyInstaller one-directory bundle; and create the private package only as a validated overlay on the already-approved public artifact.

**Tech Stack:** Python 3.10–3.13, stdlib HTTP server, SQLite, Pillow, UnityPy, Anthropic SDK, pywin32, pytest, Playwright Chromium, PyInstaller, PowerShell, GitHub Actions, GitHub CLI.

## Global Constraints

- The exact product name is `HaloCue`; UI display version is `HaloCue 0.9 Beta`; full version is `0.9.0-beta.1`.
- Public archive: `HaloCue-0.9.0-beta.1-windows.zip`.
- Private archive: `HaloCue-0.9.0-beta.1-private-windows.zip`.
- Public source and public release must contain no AA/Blue Archive artwork, audio, AssetBundles, skeleton files, generated previews, personal scripts, credentials, absolute personal paths, local caches, install records, or private planning documents.
- Personal `.skel`, `.atlas`, `.spine`, `.aap`, `.aas`, images, audio, AssetBundles, and project files are forbidden in both public and private packages.
- A Spine program may enter the private package only when the operator supplies it separately and provides an explicit redistribution authorization attestation. The private package is never uploaded by CI or attached to GitHub.
- Original HaloCue code uses MIT. Third-party software, game data, annotations, and user-supplied Spine files are not relicensed by MIT.
- The public icon is an original HaloCue asset. Never copy the local reference collection into source or releases; generated chroma-key intermediates and QA sheets remain under ignored `build/` only.
- Public source must start from a new clean history. Do not publish the current local Git history, because it contains internal documentation with personal paths.
- Preserve all unrelated changes in the current dirty worktree. Before editing a file, inspect its diff and integrate with the user's changes rather than replacing them.
- Use test-first implementation: add the failing test, confirm the intended failure, implement the smallest complete change, then run the focused test and the relevant regression set.
- Git staging, commits, remote repository creation, pushes, tags, and GitHub Release publication require fresh explicit user authorization immediately before each action. Read-only Git/GitHub checks do not.
- Every generated public artifact must be reproducible from tracked public source. No build step may silently read ignored `aa_config.json`, `llm.json`, `llm_profiles.json`, `aa_resources.json`, raw `aa_assets.db`, `out/`, `.thumbs/`, `output/`, or personal cast/script files.
