# 骨骼表情标注轮询恢复设计

## 问题

骨骼表情标注工作区在 `/api/assets/faces/job` 任意一次读取失败后直接停止轮询。界面保留上一次成功响应中的 `rendering`、`处理中` 和日志，因此一次短暂断线会被表现成永久卡死。渲染器同时只在整个渲染阶段开始和结束时报告进度，正常的长任务也缺少可见反馈。

## 方案

前端把任务轮询改成可恢复状态机。只要工作区仍打开且当前任务可能仍在运行，读取失败后就按 1.7 秒、3.4 秒、6.8 秒递增并封顶 8 秒继续重试。错误信息明确显示连接中断和自动重试，不覆盖最后一次有效的阶段、进度和日志。下一次成功响应会清零连续失败次数，并恢复正常的 850 毫秒轮询。关闭工作区或切换代次后，旧定时器不得继续请求或改写界面。

渲染器增加可选进度回调，在开始每个表情前报告当前序号、总数和 face ID，并在完成后报告已完成数量。编排层把该回调转换为现有 `rendering` 任务进度，因此前端无需新增接口字段。

## 错误与并发规则

- 网络读取失败不改变后端任务状态，也不重新提交任务。
- 轮询失败期间启动按钮保持禁用，避免同一任务重复排队。
- 后端返回 `done=true` 后停止轮询；成功和失败均沿用现有结果渲染。
- 关闭工作区会取消重试计时器；重新打开从零次失败开始。
- Spine 命令自身的 120 秒超时和失败处理保持不变。

## 测试

- JavaScript 运行时测试模拟第一次读取失败、第二次恢复为运行中、第三次完成，断言自动重试、状态恢复和最终停止。
- Python 测试用假的 Spine runner 渲染两个表情，断言进度回调按开始/完成顺序产生 `0/2`、`1/2`、`2/2`。
- 编排层测试断言渲染器回调被映射到 `rendering` 阶段。
- 最后运行相关测试、完整 pytest 和真实浏览器工作区检查。

## 非目标

本次不引入 SSE/WebSocket，不持久化跨进程任务，不改变素材库布局，也不修改 AI 视觉标注策略。
