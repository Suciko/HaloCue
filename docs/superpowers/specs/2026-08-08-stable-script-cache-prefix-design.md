# 原始剧本稳定缓存前缀设计

状态：已确认，待实现

## 问题

按场景块标注时，若先将原始剧本压缩、摘要或改写，再把新文本传给模型，原本可复用的剧本文本前缀会从首个改写 token 起失效。压缩请求本身也会额外消耗输出和推理 token，因此“更短的摘要”可能比保留原文更慢、更贵。

## 决策

对同一份剧本的一次标注运行，使用精确的原始 UTF-8 文本作为不可变缓存前缀的一部分。它不能被摘要、清洗、重排或随场景块重写。请求结构固定为：

```text
稳定前缀：标注规则 + 资源约束 + 原始剧本
动态尾部：运行记忆 + 已确认使用链 + 相关事件
用户内容：目标场景块、前后文和本次纠错说明
```

动态尾部只能位于稳定前缀之后。前后文、事件和重试提示可以随块变化，但不能进入或覆盖原始剧本块。

## Provider 边界

- Anthropic：稳定前缀作为带 `cache_control` 的首个 system 文本块；动态内容放在后续 system 块。
- OpenAI-compatible：稳定前缀必须是首条 system message 的开头；动态内容只追加在其后。服务端是否报告缓存由 usage 字段决定，应用不得伪造命中率。
- 不支持或未报告缓存的服务仍使用同一顺序，以保持请求可比性。

## 范围与限制

- 不新增“按场景摘要剧本”的请求。
- 保留对事件、使用链和方向状态的有界限制；这些是动态状态保护，不是剧本文本压缩。
- 不改变逐行标注协议、检查点、分块和推理模式。
- 不将剧本文本、API Key 或模型 reasoning 正文写入 telemetry。

## 验证

离线测试必须证明：稳定前缀包含精确原文、同一运行各块保持字节一致、动态状态和目标块位于其后。受控真实请求只记录脱敏的输入/缓存 token、命中率、请求数和耗时；在无 usage 报告时明确标为未知。
