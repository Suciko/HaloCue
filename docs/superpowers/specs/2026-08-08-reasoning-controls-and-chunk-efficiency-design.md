# 审查草稿推理控制与分块效率设计

日期：2026-08-08
状态：已确认，待实现

## 结论

推荐采用“模型能力驱动的推理控制 + 紧凑响应协议 + 任务级自适应分块 + 分阶段流式 telemetry”。默认档位为“均衡”，明确开启思考；用户选择“速度”时，在模型确实支持的前提下关闭思考。请求的 `max_tokens` 直接跟随模型最大输出能力，不再额外设置 16K/32K/64K 的 Agent 固定上限；思考量只由模型支持的推理强度控制。

该方案同时解决三个不同问题：

1. 用户看不到模型已经开始思考；
2. 每个小块重复支付长思考和重复上下文成本；
3. 模型把哈希回填、空字段装配和结构校验展开成长推理。

它不宣称流式状态能缩短真实生成时间。速度改善来自降低无效思考、缩短输出协议、按本次任务调整块大小、跳过已知失败的协议探测，以及只对真正可恢复的错误重试。

## 备选方案

### A. 能力驱动的完整方案（推荐）

每个模型记录可用能力：是否支持关闭思考、可用推理档位、参数协议、最大模型输出和最大上下文。界面只展示该模型真正支持的选项，Provider 根据供应商和端点序列化参数。推理模式只控制思考强度；分块根据当前任务特征和运行数据守住容量与失败成本边界。

优点是行为真实、可扩展且不会向不兼容接口发送伪参数；缺点是需要增加模型能力结构和针对 Provider 的映射测试。

### B. 对所有 OpenAI-compatible 接口统一发送参数

统一发送 `reasoning_effort`、`enable_thinking` 或 `thinking`。实现最少，但真实探测已经证明部分字段会被忽略，严格端点还可能直接拒绝请求。界面会产生“用户选择已生效”的错误承诺，因此不采用。

### C. 只增加“默认/速度”二档

可以快速交付，但不能满足用户选择推理强度的要求，也无法表达“不支持关闭但支持 effort”的模型能力。可以作为 A 的界面降级，不作为数据模型。

## 模型能力结构

在现有模型能力记录中增加独立的推理声明：

```json
{
  "reasoning": {
    "toggle": true,
    "efforts": ["low", "medium", "high"],
    "default": "medium",
    "wire_protocol": "deepseek_thinking"
  },
  "max_output_tokens": 384000
}
```

字段语义：

- `toggle`：能否可靠关闭思考，而不是接口是否接受一个布尔字段。
- `efforts`：已确认能够映射的离散档位；空数组表示只支持开关或仅供应商默认。
- `default`：应用新建配置的默认思考档位，必须是开启状态。
- `wire_protocol`：Provider 参数序列化规则，不由 UI 猜测。
- `max_output_tokens`：模型或连接的容量上限，不是单次任务预算。

预制模型使用本地能力目录和连接元数据。自定义模型先按精确模型名匹配目录；匹配不到时只显示“供应商默认”，不猜测可关闭或可调档。后续若连接 `/models` 返回明确推理能力，再开放相应选项。

## 用户界面

模型工作台增加“推理模式”离散控制：

- `速度`：关闭思考，副文案“生成更快，复杂场景质量可能下降”。仅在 `toggle=true` 时出现。
- `低`、`均衡`、`深入`：映射到模型支持的 effort；默认选中“均衡”。
- `供应商默认`：未知模型或无法可靠映射时的唯一安全选项。

若模型支持思考但不能关闭，不展示“速度”，并显示“此模型不支持关闭思考”。若只支持开关，显示“速度/思考”二档。保存时记录规范化的模式，不把 UI 标签直接写成 Provider 参数。

## Provider 参数映射

Provider 根据 `wire_protocol` 构造请求：

- DeepSeek Chat Completions：速度为 `thinking.type=disabled`；开启为 `thinking.type=enabled`，只在已声明支持时附加 `reasoning_effort`。
- 标准 OpenAI reasoning 模型：使用该端点官方支持的 `reasoning_effort`，不发送 DeepSeek 的 `thinking` 对象。
- Anthropic adaptive thinking：开启时使用 adaptive thinking 与 output effort；只有模型能力明确允许关闭时才提供关闭选项。
- 未知 OpenAI-compatible：不发送任何推理扩展字段，保留供应商默认行为。

DeepSeek 官方连接直接使用已经验证可用的 `json_object` 路径，跳过必然返回 HTTP 400 的严格 `json_schema` 首次探测；本地仍执行完整 Schema 与 Annotation Protocol 校验。

## 紧凑响应协议

模型只返回目标行在当前块中的短索引和非空演出字段，不再复制 `source_id`、64 位 `text_fingerprint`，也不再输出值为空的可选字段。示例：

```json
{"lines":[{"i":3,"face":"05","emo":"疑问"}],"state_delta":{},"memory_events":[]}
```

程序在校验前按本次 TARGET 表恢复 `source_id`、`text_fingerprint` 和协议默认值。索引越界、重复索引或目标缺失仍由本地校验拒绝。资源 allowlist、状态合并、检查点和最终完整行结构保持不变。

提示词明确要求：每行一次决策；不复述规则、原文、资源表或哈希；不枚举候选并来回比较；没有明确演出价值时直接省略字段；语义选择结束后立即返回 JSON。程序负责确定性校验，模型不承担 JSON 完整性复核。

## 容量与分块

配置中分离三个概念：

1. `max_output_tokens`：连接/模型最大输出，来自能力发现或用户手动覆盖。
2. `context_window_tokens`：模型最大上下文，用于约束“稳定前缀 + 动态尾部 + 本次 TARGET + 最大输出预留”。接口没有报告时使用已验证目录；仍未知时采用保守兼容策略并标明来源未知。
3. `agent_target/soft/hard_lines`：本次任务的初始场景块目标和边界，不是跨模型、跨剧本的全局最佳值。

初始块大小由当前任务估算，不按模型名称写死：统计剧本目标行数、场景边界、参与角色数、资源约束规模、稳定前缀 token 估算、动态状态 token 估算和紧凑协议的预计输出。分块必须保留自然场景边界，并保证输入与模型最大输出预留之和不超过上下文窗口。

运行中只在当前任务内学习：连续成功且 reasoning/正文比例、墙钟和输出容量均有余量时，允许下一场景适度放大；空正文、截止时间、`finish_reason=length`、协议缺失或异常高 reasoning/正文比例时缩小后续块。调整采用有限档位并设置迟滞，避免每个请求来回振荡。任务结束后的数据只用于诊断和未来离线校准，不直接写成所有剧本的永久“最佳块数”。

模型最大上下文不是“整篇永远一次请求”的理由。块越大，语义选择组合数、正文装配和失败重做成本越高；优化目标是降低总未命中 token、总墙钟和失败重做成本，而不是单独追求请求最少或缓存命中百分比最高。

## 流式状态与指标

每次请求分别记录并向 Job 发出：

- `request_started`：请求已发出；
- `first_sse`：服务端开始返回事件；
- `reasoning`：收到非空思考增量，只累计字符/token 和时间，不保存正文；
- `content`：收到可见 JSON 增量；
- `completed`：finish reason、usage 和总耗时；
- `retrying` / `subdividing`：明确原因和次数。

界面依次显示“等待模型响应”“模型思考中 · 已用时 N 秒”“模型正在生成草稿 · 已接收 N 字符”。思考正文不进入浏览器、日志、草稿或检查点。任务结果增加首 SSE、首思考、首正文、reasoning/content 计数、请求级耗时和缓存命中数据。

请求级脱敏 metrics 必须在每次请求结束时立即写出，不能等整组基准结束后一次性输出；这样即使 30 分钟外部超时，也能定位卡在哪个配置和请求。每条记录额外保存稳定前缀哈希、动态尾部哈希、Schema 哈希、目标行数、输入/缓存命中/未命中 token、reasoning/content token、首思考/首正文时间和本次分块决策原因。哈希只用于证明请求片段是否稳定，不保存剧本文本。

## 重试与截止边界

- 只对 429、500、502、503、504、连接重置和超时做最多 2 次有限退避重试，并分别计数。
- 非瞬时 4xx、非法资源、身份错误和普通 Schema 类型错误不走传输重试。
- `finish_reason=stop` 且正文为空、同时已经产生 reasoning 时最多重试一次；重试临时降低一级推理强度，并明确要求直接返回最终 JSON。无法降低的模型保持原档但仍只重试一次。
- 其他协议内容错误最多一次同尺寸纠正；第二次失败保留检查点并返回具体错误。
- 只有 `finish_reason=length`、确认截断或目标行因容量缺失才缩块。
- 请求达到产品级总时长上限时停止当前请求并保留已完成检查点；界面说明可切换均衡/速度模式后继续。

## 测试顺序

1. 先用 fake stream 写失败测试，覆盖 reasoning 早于 content、未知模型不发送参数、DeepSeek 开关映射和请求级 metrics。
2. 实现紧凑响应 Schema、短索引恢复和本地完整性校验。
3. 实现能力结构、Provider 参数映射和模型最大输出/上下文分离。
4. 实现模型工作台推理模式滑块和不支持状态。
5. 实现空正文降级重试、瞬时传输重试、截止时间及请求级脱敏 metrics。
6. 实现任务级初始分块估算和有限档位自适应策略。
7. 跑现有 Provider、Agent、模型工作台和 UI 回归。
8. 用小、中、长三类合成剧本验证策略不会把一次结果泛化为全局块数。
9. 最后用 266 行历史剧本完整生成 V3，与本次 V2 基准比较墙钟、未命中 token、reasoning token、正文 token、请求/重试/缩块和背景保留。

## 验收标准

- 新模型默认开启思考；支持关闭的模型可选速度模式。
- 不支持关闭或能力未知的模型不展示虚假关闭选项，也不盲发参数。
- DeepSeek 关闭思考真实请求不产生 reasoning 增量；开启时界面能在首正文前显示“模型思考中”。
- 请求 `max_tokens` 使用模型最大输出；思考强度不会再隐式改写请求容量。
- 最大上下文独立保存并参与每次任务的输入与输出容量校验。
- 已知 DeepSeek 官方连接不再先支付一次必失败的严格 Schema 请求。
- 紧凑协议不再要求模型复制哈希或空字段，本地恢复后的完整结果通过原有协议校验。
- 分块决策只对当前任务生效，不存在写死的跨剧本“最佳块数”。
- 瞬时服务错误有界重试；内容错误不重复烧多次完整请求。
- 每个请求都有可用于复盘的脱敏阶段指标，即使任务最终超时或失败。
- 逐行身份覆盖、状态合并、检查点恢复和资源 allowlist 回归全部通过。
