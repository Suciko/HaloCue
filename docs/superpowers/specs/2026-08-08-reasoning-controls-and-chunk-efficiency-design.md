# 审查草稿推理控制与分块效率设计

日期：2026-08-08
状态：待确认

## 结论

推荐采用“模型能力驱动的推理控制 + 按模式设置任务预算和分块 + 分阶段流式 telemetry”。默认档位为“均衡”，明确开启思考；用户选择“速度”时，在模型确实支持的前提下关闭思考。模型公布的最大输出只作为容量上限，不再直接等同于每次审查请求的输出预算。

该方案同时解决三个不同问题：

1. 用户看不到模型已经开始思考；
2. 每个小块重复支付长思考和重复上下文成本；
3. 六位数模型上限放大单次长尾与费用风险。

它不宣称流式状态能缩短真实生成时间。速度改善来自关闭/降低思考、减少请求次数、跳过已知失败的协议探测，以及只对真正可恢复的错误重试。

## 备选方案

### A. 能力驱动的完整方案（推荐）

每个模型记录可用能力：是否支持关闭思考、可用推理档位、参数协议、最大模型输出。界面只展示该模型真正支持的选项，Provider 根据供应商和端点序列化参数。分块与任务输出预算随推理模式变化，并用运行数据守住容量边界。

优点是行为真实、可扩展且不会向不兼容接口发送伪参数；缺点是需要增加模型能力结构和针对 Provider 的映射测试。

### B. 对所有 OpenAI-compatible 接口统一发送参数

统一发送 `reasoning_effort`、`enable_thinking` 或 `thinking`。实现最少，但真实探测已经证明部分字段会被忽略，严格端点还可能直接拒绝请求。界面会产生“用户选择已生效”的错误承诺，因此不采用。

### C. 只增加“默认/速度”二档

可以快速交付，但不能满足用户选择推理强度的要求，也无法表达“不支持关闭但支持 effort”的模型能力。可以作为 A 的界面降级，不作为数据模型。

## 模型能力结构

在现有模型能力记录中增加独立的推理声明：

```json
{
  "reasoning": {
    "toggle": true,
    "efforts": ["low", "medium", "high"],
    "default": "medium",
    "wire_protocol": "deepseek_thinking"
  },
  "max_output_tokens": 384000
}
```

字段语义：

- `toggle`：能否可靠关闭思考，而不是接口是否接受一个布尔字段。
- `efforts`：已确认能够映射的离散档位；空数组表示只支持开关或仅供应商默认。
- `default`：应用新建配置的默认思考档位，必须是开启状态。
- `wire_protocol`：Provider 参数序列化规则，不由 UI 猜测。
- `max_output_tokens`：模型或连接的容量上限，不是单次任务预算。

预制模型使用本地能力目录和连接元数据。自定义模型先按精确模型名匹配目录；匹配不到时只显示“供应商默认”，不猜测可关闭或可调档。后续若连接 `/models` 返回明确推理能力，再开放相应选项。

## 用户界面

模型工作台增加“推理模式”离散控制：

- `速度`：关闭思考，副文案“生成更快，复杂场景质量可能下降”。仅在 `toggle=true` 时出现。
- `低`、`均衡`、`深入`：映射到模型支持的 effort；默认选中“均衡”。
- `供应商默认`：未知模型或无法可靠映射时的唯一安全选项。

若模型支持思考但不能关闭，不展示“速度”，并显示“此模型不支持关闭思考”。若只支持开关，显示“速度/思考”二档。保存时记录规范化的模式，不把 UI 标签直接写成 Provider 参数。

## Provider 参数映射

Provider 根据 `wire_protocol` 构造请求：

- DeepSeek Chat Completions：速度为 `thinking.type=disabled`；开启为 `thinking.type=enabled`，只在已声明支持时附加 `reasoning_effort`。
- 标准 OpenAI reasoning 模型：使用该端点官方支持的 `reasoning_effort`，不发送 DeepSeek 的 `thinking` 对象。
- Anthropic adaptive thinking：开启时使用 adaptive thinking 与 output effort；只有模型能力明确允许关闭时才提供关闭选项。
- 未知 OpenAI-compatible：不发送任何推理扩展字段，保留供应商默认行为。

DeepSeek 官方连接直接使用已经验证可用的 `json_object` 路径，跳过必然返回 HTTP 400 的严格 `json_schema` 首次探测；本地仍执行完整 Schema 与 Annotation Protocol 校验。

## 容量与分块

配置中分离三个概念：

1. `max_output_tokens`：连接/模型最大输出，来自能力发现或用户手动覆盖。
2. `annotation_output_budget`：单次标注请求预算，由应用按模式给出保守值，不超过模型上限。
3. `agent_target/soft/hard_lines`：场景块目标和边界。

第一版采用已验证数据支持的保守策略：

| 模式 | 初始分块 | 单次预算策略 | 说明 |
|---|---|---|---|
| 速度 | 50/60/72 | `min(模型上限, 任务预算)` | 266 行真实样本 5 次请求成功，最快 174.434 秒 |
| 均衡 | 40/50/60 | 保守任务预算，首块按 usage 校准 | 默认开启思考；在 telemetry 完成前不使用 72 行硬上限 |
| 深入 | 20/24/30 | 较高但有界的任务预算 | 用户明确选择质量优先；界面提示预计更慢 |
| 未知/供应商默认 | 40/50/60 | 沿用已保存任务预算 | 不假设是否存在隐藏思考 |

模型六位数上限不得自动成为 `annotation_output_budget`。任务预算需要容纳结构化正文和合理 reasoning，但必须设置产品级上界；接近预算或 `finish_reason=length` 才触发容量缩块。第一块成功后记录 output tokens/target 和 finish reason，只允许在有足够余量时放大后续块；一次容量失败后继续沿用现有的任务内安全上限学习。

高思考 60 行对比已在 30 分钟外部上限内失败且没有逐组日志，因此均衡和深入模式的最终数值必须在 telemetry 落地后用小规模阶梯测试校准，不能依据这次超时冒进到 60/72 行。

## 流式状态与指标

每次请求分别记录并向 Job 发出：

- `request_started`：请求已发出；
- `first_sse`：服务端开始返回事件；
- `reasoning`：收到非空思考增量，只累计字符/token 和时间，不保存正文；
- `content`：收到可见 JSON 增量；
- `completed`：finish reason、usage 和总耗时；
- `retrying` / `subdividing`：明确原因和次数。

界面依次显示“等待模型响应”“模型思考中 · 已用时 N 秒”“模型正在生成草稿 · 已接收 N 字符”。思考正文不进入浏览器、日志、草稿或检查点。任务结果增加首 SSE、首思考、首正文、reasoning/content 计数、请求级耗时和缓存命中数据。

请求级脱敏 metrics 必须在每次请求结束时立即写出，不能等整组基准结束后一次性输出；这样即使 30 分钟外部超时，也能定位卡在哪个配置和请求。

## 重试与截止边界

- 只对 429、500、502、503、504、连接重置和超时做最多 2 次有限退避重试，并分别计数。
- 非瞬时 4xx、非法资源、身份错误和普通 Schema 类型错误不走传输重试。
- 协议内容错误最多一次同尺寸纠正；第二次失败保留检查点并返回具体错误。
- 只有 `finish_reason=length`、确认截断或目标行因容量缺失才缩块。
- 请求达到产品级总时长上限时停止当前请求并保留已完成检查点；界面说明可切换均衡/速度模式后继续。

## 测试顺序

1. 先用 fake stream 写失败测试，覆盖 reasoning 早于 content、未知模型不发送参数、DeepSeek 开关映射和请求级 metrics。
2. 实现能力结构、Provider 参数映射和任务预算分离。
3. 实现模型工作台推理模式控件和不支持状态。
4. 实现瞬时传输重试、截止时间及请求级脱敏 metrics。
5. 跑现有 Provider、Agent、模型工作台和 UI 回归。
6. 用 3 行真实样本验证速度/均衡状态和严格协议。
7. 用 60 行阶梯测试校准均衡分块；每次只增加一个块级别，达到截止时间立即停止。
8. 最后跑 266 行速度模式完整基准；均衡模式只有在 60 行阶梯通过后才跑完整长稿。

## 验收标准

- 新模型默认开启思考；支持关闭的模型可选速度模式。
- 不支持关闭或能力未知的模型不展示虚假关闭选项，也不盲发参数。
- DeepSeek 关闭思考真实请求不产生 reasoning 增量；开启时界面能在首正文前显示“模型思考中”。
- 模型最大输出与标注任务预算分别保存和使用，六位数模型上限不会放大每次请求预算。
- 已知 DeepSeek 官方连接不再先支付一次必失败的严格 Schema 请求。
- 266 行速度模式保持 5 至 6 个请求，无协议重试和无缩块。
- 瞬时服务错误有界重试；内容错误不重复烧多次完整请求。
- 每个请求都有可用于复盘的脱敏阶段指标，即使任务最终超时或失败。
- 逐行身份覆盖、状态合并、检查点恢复和资源 allowlist 回归全部通过。
