# 双角色模型管理设计

## 目标

重构现有模型接口设置，把“供应商连接”“具体模型”和“任务用途”分开管理。用户可以使用一个支持文字和图片的全能模型，也可以让便宜的文字模型承担基础任务、让可选的视觉模型只承担图片识别任务。

设置界面以管理效率为主。主界面只展示名称、能力、状态和操作；注册方法、费用差异、协议解释和完整接入步骤统一放入帮助说明。

## 已确认的产品原则

- 基础模型必需，负责全部纯文字 AI 请求。
- 图片识别模型可选，只在确实需要读取图片的任务中调用。
- 独立视觉模型未设置时，可以复用已经通过图片测试的基础模型。
- 没有任何可用视觉模型时，跳过 AI 识别并保留手动处理入口，不阻塞其他功能。
- 视觉调用失败时不静默切换模型，避免用户不知情地产生额外费用。
- API Key 继续由 Windows 凭据管理器保存，不写入配置 JSON、日志或公共 API 响应。
- 模型能力以实际测试结果为准，不仅凭供应商或模型名称推断。

## 界面结构

### 第一层：任务用途总览

设置抽屉的“AI 模型”区域只显示两项：

1. **基础模型**：供应商名称、模型名称、文字测试状态和“更换”。
2. **图片识别模型**：当前独立视觉模型或“未设置”、图片测试状态和“更换”或“添加模型”。

这一层不显示 API Key、Base URL、接口协议、费用建议或教程段落。右上角提供帮助入口。

### 第二层：选择模型

点击“更换”后进入模型选择页。页面按当前用途自动筛选：

- 更换基础模型时显示具有文字能力的已配置模型。
- 更换图片识别模型时优先显示图片测试通过的模型，同时允许查看未测试模型。
- 每项只显示供应商、模型名、能力标签、测试状态和“使用”或“测试”。
- 支持按名称搜索和按供应商、能力、测试状态筛选。
- 图片识别模型列表提供“关闭图片识别”。
- 页面底部只有一个“添加模型”动作，进入第三层。

### 第三层：供应商与模型管理

“添加模型”进入接近 Cherry Studio 的供应商管理页：

- 左侧或顶部是已配置连接与供应商预设。
- 选择预设后自动填充内部协议和 Base URL。
- 表单包含连接名称、API Key、API 地址和高级设置。
- 供应商预设提供官网或“获取 API Key”的外部链接。
- 保存连接后可以读取模型列表；读取失败时允许手动输入模型 ID。
- 一个供应商连接可以保存多个具体模型。
- 同一供应商允许建立多个连接，例如个人账号和公司账号。
- 自定义连接支持 OpenAI-compatible 和 Anthropic 两种现有内部协议。

主流程按钮使用“添加模型”“测试”“保存并使用”等短命令。详细字段解释只出现在帮助页；高级技术字段默认折叠。

## 数据模型

### ProviderConnection

代表一个可复用的 API 连接：

```json
{
  "id": "connection-id",
  "name": "DeepSeek 个人账号",
  "service_preset": "deepseek",
  "protocol": "openai",
  "base_url": "https://api.deepseek.com/v1"
}
```

API Key 使用连接 ID 作为凭据标识，单独保存到 Windows 凭据管理器。

### ModelEntry

代表连接下的一个模型：

```json
{
  "id": "model-entry-id",
  "connection_id": "connection-id",
  "model": "deepseek-chat",
  "max_tokens": 16000,
  "text_status": "passed",
  "vision_status": "unsupported"
}
```

能力状态分别取 `untested`、`passed`、`failed` 或 `unsupported`。只有连接测试可以写入 `passed`；预设可以将明确不支持的能力初始化为 `unsupported`，但不能初始化为 `passed`。

### ModelAssignments

记录任务用途：

```json
{
  "base_model_id": "model-entry-id",
  "vision_mode": "separate",
  "vision_model_id": "vision-model-entry-id"
}
```

`vision_mode` 取值：

- `separate`：使用独立视觉模型。
- `base`：复用基础模型，基础模型必须已通过图片测试。
- `disabled`：关闭 AI 图片识别。

## 请求路由

纯文字调用统一解析 `base_model_id`。当前纯文字调用点包括剧本初审、演出标注和其他只提交文字的 AI 操作。

视觉调用按以下顺序解析：

1. `vision_mode=separate` 时使用 `vision_model_id`。
2. `vision_mode=base` 时使用 `base_model_id`，并校验其 `vision_status=passed`。
3. `vision_mode=disabled` 时不创建 AI 视觉请求。

背景图片标注、角色表情识别和其他 `complete_json_vision` 调用统一通过视觉路由器获取 Provider，不能再直接读取“当前模型”。

同一个全能模型可以同时被两个用途引用，不复制连接、密钥或模型记录。

## 状态与错误处理

- 未配置图片模型：相关任务显示“未设置”和“添加模型”；文字功能不受影响。
- 视觉任务被关闭：任务进入可手动处理状态，不作为系统错误。
- 视觉调用失败：保留已经完成的非视觉结果，任务标为“部分完成”，提供“重试”“改用基础模型”“手动处理”。
- “改用基础模型”是单次明确操作，不自动改变全局分配；基础模型必须已通过图片测试。
- 基础模型缺少密钥或连接失败：AI 文字操作显示“基础模型不可用”和“打开模型设置”；手动编辑、审查、编译和安装仍可继续。
- 保存连接或模型不要求测试通过，未测试状态必须始终可见。
- 删除仍被模型或任务用途引用的连接时阻止删除，并指出需要先解除的引用。
- 删除当前分配的模型时阻止删除，或要求用户先选择替代模型。
- 公共错误只给出可执行结论，不包含 API Key、Authorization、物理文件路径或堆栈。

## 旧配置迁移

现有每个 profile 自动迁移为：

- 一条 `ProviderConnection`，继承名称、预设、协议和 Base URL。
- 一条 `ModelEntry`，继承模型名和最大输出。
- 原 active profile 对应的模型成为 `base_model_id`。
- 原 `vision=true` 不能直接视为图片测试通过；迁移后为 `untested`，用户测试通过后才可设为视觉用途。
- 原凭据沿用现有凭据目标或在迁移事务中安全改名，任何失败不得丢失旧密钥。

迁移应幂等。首次成功写入新版本后保留可识别的 schema version，后续启动不重复生成连接和模型。

## 验收与测试

### 存储与迁移

- 连接、模型、用途可以独立保存和读取。
- 同一连接可以关联多个模型。
- 密钥不进入 JSON、日志或公共 API。
- 旧 profile 迁移幂等，active profile 成为基础模型，密钥保持可用。
- 被引用连接和模型不能误删。

### 路由

- 所有纯文字调用只使用基础模型。
- `separate`、`base`、`disabled` 三种视觉策略分别走正确路径。
- 未通过图片测试的模型不能被设为 `base` 视觉策略。
- 视觉失败不自动改用其他模型，也不破坏已完成结果。
- 缺少视觉模型不阻塞文字 AI、手动编辑或编译。

### 界面

- 第一层在桌面和手机宽度下只显示两个用途项及必要操作。
- “更换”进入按用途筛选的模型列表，“添加模型”才进入供应商配置。
- 默认界面不出现教程段落、费用建议和协议解释。
- 模型列表准确呈现文字、图片、未测试和失败状态。
- 无模型、无密钥、测试中、测试失败和部分完成状态都有稳定布局与明确操作。

### 安全与错误

- 前后端错误响应对密钥、认证头、绝对路径和堆栈进行脱敏。
- 连接测试使用小型固定请求；视觉测试使用本地生成的小图片，不读取用户素材。
- 测试失败不把模型错误标为已通过。

## 实施边界

本轮包含模型配置、路由、迁移、帮助说明和相关测试。不增加用量统计、价格计算、自动选择最便宜模型、自动故障转移或第三种任务角色。
