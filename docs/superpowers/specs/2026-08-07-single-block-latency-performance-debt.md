# 单场景块生成延迟性能债记录

状态：`OPEN`
建立日期：2026-08-07
责任边界：审查草稿 Annotation Agent 的单次模型请求与单块端到端耗时

## 为什么单独记录

本轮先处理确定性较高、可以直接减少失败和浪费的问题：

- `state_delta` 可选字段返回 `null` 时归一化为“不更新”；
- Provider 不再因内容 schema 错误静默重发完整请求；
- 容量错误、协议错误和连接错误分开处理；
- 容量成功缩块后，当前任务记住安全块大小；
- Provider 输出真实流式活动，Job/UI 显示等待首段、持续接收、重试和缩块；
- 记录实际模型、请求、重试、缩块、输入/输出和缓存报告。

这些改动可以让用户知道“现在在等什么”，也可以阻止已经确认的无效重试，但它们不能证明模型本身会更快完成一个场景块。尤其是把 `max_tokens` 从五位数改成六位数只改变截断上限，不等于提高生成吞吐，也可能扩大单次异常输出的成本上界。

因此本文件不允许被标记为“已由流式输出解决”。流式输出主要改善感知延迟；单块总耗时必须另行测量、定位和验收。

## 2026-08-07 真实草稿端到端冒烟

这次首次实际调用 Token Rhythm 的 completion，并完整写出草稿文件；此前只有 `/models` 冒烟，不能算生成验收。

| 运行 | 输入 | 结果 | 请求/重试/缩块 | 首个可见正文 | 总耗时 | 用量 |
|---|---:|---|---:|---:|---:|---|
| Token Rhythm 小草稿 | 3 行台词 | 草稿写出，5 行含场景和背景指令 | 1 / 0 / 0 | 30.535 秒 | 36.920 秒 | 输入 14,061，输出 3,184，缓存命中 0% |
| DeepSeek 官方小草稿 | 3 行台词 | 同一输入成功写出，6 行含过渡和背景请求 | 1 / 0 / 0 | 27.467 秒 | 29.881 秒 | 输入 15,050，输出 3,837，缓存命中 22.96% |
| Gemini 3.6 Flash 代理 | 3 行台词 | 两次都把 `move` 返回为非整数，纠正后仍失败 | 2 / 1 / 0 | 首次 8.161 秒 | 17.445 秒 | 输入 48,140，输出 1,159，缓存命中 25.47% |
| 25 行失败冒烟 | 25 行台词 | 唯一场景块收到 HTTP 503，草稿生成失败 | 0 个完成请求 / 0 / 0 | 未收到首段 | 5.221 秒 | 供应商未返回 usage |

这张表中的旧 `first_delta_ms` 只在 `delta.content` 非空时赋值，因此 30.535 秒和 27.467 秒不是严格意义上的 TTFT，而是“首个可见正文延迟”。它们不能证明此前没有 token，也不能把这段时间全部归因于供应商排队。`max_tokens=384000` 没有让 Token Rhythm 样本输出到上限；官方样本使用当前官方 profile 的 `max_tokens=16000`，同样正常 `finish_reason=stop`。

Gemini 代理的首个可见正文更早，但当前链路没有可靠执行严格 schema：第一次响应类型错误后 Agent 已经追加纠正提示并完整重发，第二次仍返回非整数 `move`。只修改 schema 描述为“未移动填 0”做运行时对照也没有消除失败，因此不能把它当作已可替换的快速模型；后续需允许受控的空值哨兵并在协议层归一化，或改用真正执行 JSON Schema 的 Gemini 接口后再测。HTTP 503 样本同时表明当前 `LLMError` 对瞬时服务错误直接按 fatal 抛出，Annotation Agent 没有有限退避重试，因此一次供应商瞬时繁忙就能把整次草稿标为失败。

### 首 token 口径复核

2026-08-07 对原始 SSE 做了只记录字段名、字符串长度和时间戳的脱敏检查，没有保存或输出任何思考正文：

| 请求 | 首个 SSE | 首个非空思考 | 首个可见正文 | 总耗时 | 脱敏计数 |
|---|---:|---:|---:|---:|---|
| DeepSeek 官方短逻辑题 | 0.146 秒 | 0.470 秒 | 1.908 秒 | 2.059 秒 | reasoning 832 字符，content 97 字符 |
| DeepSeek 官方真实 3 行标注提示 | 0.201 秒 | 0.700 秒 | 154.750 秒 | 158.268 秒 | reasoning 21,135 字符，content 2,046 字符 |
| Gemini 3.6 Flash 代理短逻辑题 | 3.023 秒 | 未返回独立思考字段 | 3.023 秒 | 3.053 秒 | content 23 字符，`finish_reason=length` |

DeepSeek 两次都在 `delta.reasoning_content` 中先返回思考，随后才在 `delta.content` 中返回可见 JSON。真实标注请求的 completion usage 为 12,247 tokens，其中绝大部分时间和字符量发生在可见正文之前。这证明当前慢等待的主要成分之一是模型长思考，不是网络一直没有首 token；旧 UI 把思考阶段错误显示成了“等待首段”。Gemini 代理没有暴露独立思考字段，所以只能确认首个可见正文时间，不能据此断言它没有隐藏思考。

同一次 DeepSeek 标注探测中，严格 `json_schema` 请求先收到 HTTP 400，随后按生产代码的 `json_object` 兼容路径成功。该协议探测会增加首次请求开销，但 158 秒样本的主体仍是兼容请求内部约 154 秒的思考阶段。

当前 `llm.json` 的 Agent 参数为 `agent_target_lines=20`、`agent_soft_limit=24`、`agent_hard_limit=30`。离线构造 200 行单场景时实际得到 9 个块（24 行 × 8 + 8 行），不是旧基线常见的 4 个 50 行块；即使每块只等待约 30 秒，固定首段等待也会累积到数分钟，任何 503、协议纠正或容量缩块都会继续放大总时长。

因此本问题的第一批可验证修复顺序应为：

1. 对 429/500/502/503/504、连接重置和超时做有上限的指数退避，并把重试单独计入 metrics；非瞬时的 4xx 和 schema 错误仍然快速失败。
2. 在同一资源表和模型上把块大小从 20/24/30 与 40/50/60 做受控对比，不能直接把所有模型硬改成大块。
3. 保留流式状态，但把每块计时拆为首个 SSE、首个思考片段、首个可见正文、持续接收和完成；思考流只用于活动与计数，绝不写入草稿或日志正文。
4. 用连续 3 次真实 200/240 行测试测量首事件、首思考、首正文、请求数、失败重试和缓存读/未命中，达到关闭条件前不宣称性能修复。

## 当前根因假设

按可证伪性和预计影响排序：

1. **Provider 协议兼容重发。** 内容/schema 解析失败现在会直接暴露给 Agent，不再静默重发。仍然保留的重发只发生在供应商以 HTTP 400 明确拒绝 `response_format` 时，用于学习当前连接的协议能力。后续基准仍必须记录这类协议重发次数，确认每个连接只在首次能力探测时支付一次额外成本。
2. **每块输出量和结构化协议开销过大。** 一个块必须返回每行多个字段、指纹、状态增量、事件和可选 beats；output tokens/target 需要由新 telemetry 记录，不能再靠总账反推。
3. **模型长思考被误记为首段等待。** 已确认 DeepSeek 在真实标注提示下 0.7 秒开始 `reasoning_content`，约 154.8 秒才开始 `content`。需要研究该模型是否支持受控关闭/限制思考，并对比关闭后的结构正确率，不能继续把 `first_delta_ms` 当作 TTFT。
4. **模型可见正文生成吞吐低。** 需要分别计算思考阶段和正文阶段的 tokens/sec，而不是只看请求总时长；思考 token、隐藏 reasoning 或供应商计费字段也要单独记录（若接口提供）。
5. **输入前缀/缓存边界不稳定。** `static_system`、易变上下文、场景窗口和重试提示的排列可能让缓存前缀失效；缓存命中率必须按请求和模型报告，不能只看一次供应商截图。
6. **最大输出设置放大思考长尾和费用上界。** `384000` 能避免错误的五位数上限截断，但对会消耗 reasoning tokens 的模型也允许更长思考。需要记录 finish reason、思考/正文 token、实际 output tokens 和是否接近上限；不能把六位数推荐值当作默认性能优化。
7. **块目标大小不适配模型。** 当前目标/软上限/硬上限是静态配置；可靠性计划会先学习容量安全上限，但不假设更小块一定更快，因为更小块会增加请求次数和重复上下文。

## 2026-08-08 分块与思考模式基准

使用 `out/drafts/draft-998e165b514f/source.txt` 的真实长剧本作为固定样本。源文件包含 537 个物理行、266 个台词目标、2 个场景，其中第一场 246 个目标、第二场 20 个目标。测试不保存模型思考正文或 Authorization 信息。

### 关闭思考的完整端到端结果

DeepSeek 官方接口使用 `thinking={"type":"disabled"}`，并跳过该接口已知不支持的严格 `json_schema` 探测。所有完成响应仍经过真实 JSON Schema、Annotation Protocol、状态合并和检查点提交。

| 目标/软上限/硬上限 | 总耗时 | 请求 | 重试 | 缩块 | 输入 tokens | 输出 tokens | 缓存率 |
|---|---:|---:|---:|---:|---:|---:|---:|
| 20/24/30 | 200.708 秒 | 13 | 1 | 0 | 245,702 | 43,072 | 76.58% |
| 40/50/60 | 179.497 秒 | 6 | 0 | 0 | 125,212 | 39,505 | 66.24% |
| 50/60/72 | 174.434 秒 | 5 | 0 | 0 | 107,964 | 39,034 | 64.50% |

在关闭思考的条件下，5 块方案是本轮最快结果：相对 20/24/30 总耗时降低约 13%，输入 tokens 降低约 56%，请求从 13 次降到 5 次，并且没有重试或缩块。缓存率百分比下降不代表费用增加；由于重复上下文大幅减少，缓存命中和未命中的输入总量都更低。

### 开启高思考的边界测试

随后从同一剧本截取前 60 个连续台词目标，以 `thinking={"type":"enabled"}`、`reasoning_effort=high`、任务输出预算 16,000 进行真实对比，计划顺序执行 20/24/30 与 50/60/72 两组。整个测试进程在 1,804 秒达到外部 30 分钟上限，且 PowerShell 管道没有在超时前交付分组日志，因此不能声称其中任一组已成功，也不能据此断言是大块请求单独超时。

2026-08-08 将两种块大小拆开做单请求脱敏复核后，已经定位大块的具体失败机制：

| 目标行 | 首 SSE | 首 reasoning | 首 content | 总耗时 | reasoning 字符 | content 字符 | completion | finish reason | 结果 |
|---:|---:|---:|---:|---:|---:|---:|---:|---|---|
| 24 | 0.584 秒 | 1.646 秒 | 63.835 秒 | 78.925 秒 | 17,334 | 9,735 | 12,125 | `stop` | 请求正常结束 |
| 60 | 0.187 秒 | 0.725 秒 | 109.280 秒 | 119.298 秒 | 25,539 | 6,263 | 15,998 | `length` | JSON 截断，Schema/协议无法解析 |

60 行请求并没有在服务端静默等待：它从 0.725 秒起持续返回 reasoning SSE，但在 16,000 completion 预算的大部分已经被思考消耗后才开始正文，最终正好撞上输出上限。响应只留下半截 JSON，生产 Provider 会将其归类为容量错误；Agent 随后按 60→50→30→20→10→5 的候选上限逐级切分。每一次容量尝试都可能再次完整支付长 reasoning，因此原来的顺序基准由“小块多次思考 + 大块截断后的缩块链”累积到外部 30 分钟超时。

当前 `OpenAIProvider.timeout=180` 是 socket 读超时，不是单请求墙钟截止。reasoning SSE 一直有数据就会持续刷新读取活动，因此它不能终止这种长思考请求。同时 `_stream_completion_text()` 只累计 `delta.content`，忽略 `delta.reasoning_content`；所以 UI 虽然后台持续收包，仍表现为一直等待首段。这两个行为共同解释了“用户看起来卡死，但服务器其实一直在烧 reasoning token”。

这组证据还表明，简单把任务预算从 16K 提到模型公布的六位数上限，只会让 60 行请求有机会继续生成更长 reasoning，并显著扩大单次费用和墙钟上界。正确修复是先按思考模式限制块大小和任务预算、记录 reasoning 活动、设置产品级墙钟截止，再根据成功请求的 tokens/target 逐步放大；不能把模型容量上限直接当作任务预算。

### 已验证的思考开关

同一真实 3 行标注提示在 DeepSeek 官方接口上的对照如下：

| 模式 | 首思考 | 首正文 | 总耗时 | completion | 协议结果 |
|---|---:|---:|---:|---:|---|
| 默认思考 | 0.700 秒 | 154.750 秒 | 158.268 秒 | 12,247 tokens | 一次通过 |
| 关闭思考 | 无 | 0.850 秒 | 3.463 秒 | 617 tokens | 一次通过 |

短请求参数探测表明，DeepSeek 官方兼容端点只有 `thinking.type=disabled` 能可靠关闭思考；单独发送 `reasoning_effort=low` 没有形成可靠降档，`enable_thinking=false` 也未生效。因此推理参数必须按供应商和端点映射，不能对所有 OpenAI-compatible 服务统一盲发字段。

## 后续调查计划

这不是第一轮修复的执行内容；只有可靠性和上限计划完成并通过离线/小型真实冒烟后，才开始本节。

### 1. 建立固定基准

使用同一份 240 行、同一资源索引、同一提示版本、同一模型连接，分别运行 5、10、20、50 行目标块；每个配置至少重复 3 次。每次记录：

- request start、first SSE、first reasoning、first content、last delta、complete 时间；
- actual model、chunk size、input/output tokens、finish reason；
- retries、subdivisions、response-format fallback 次数；
- cache read/miss/reported、首段前是否有 reasoning 字段；
- output tokens/target、tokens/sec、请求成本（若供应商给出价格）。

实验只保存脱敏指标和请求 fingerprint，不保存提示词、脚本正文或响应正文。

### 2. 做四组可控对比

| 对比 | 变量 | 目的 |
|---|---|---|
| A | strict JSON schema vs 已明确兼容的 json_object | 证明是否仍存在格式协议额外延迟 |
| B | `max_tokens=16000/64000/384000`，其他不变 | 分离输出上限对 TTFT、finish reason 和长尾的影响 |
| C | 5/10/20/50 目标行 | 估算每块固定开销与每行边际开销 |
| D | Gemini 与 `deepseek-v4-flash` 同一 fixture | 区分供应商服务延迟和本地 Agent 开销 |

每组先跑离线 fake provider 验证计时器，再做受控真实请求；真实请求数量和预算必须先确认，避免为了测量再次造成大额消耗。

### 3. 按证据选择后续改动

- 若首个 SSE 占主要耗时：研究连接复用、供应商队列、请求体大小和模型服务端路由；不先改标注语义。
- 若 reasoning 到 first content 占主要耗时：优先验证关闭/限制思考、提示约束和模型替代，对照严格结构正确率与费用。
- 若可见正文生成吞吐占主要耗时：减少无必要的输出字段/解释，并比较结构化格式；保持逐行覆盖和身份校验。
- 若固定协议开销占主要耗时：压缩静态资源表和可变上下文，验证缓存前缀稳定性；不删除必要的状态/事件证据。
- 若缩块/重试占主要耗时：继续改错误分类和容量估算；不把所有错误都归为“输出太大”。
- 若 max token 只影响截断而不影响时延：保留自动能力匹配，不把它宣传为性能修复。

## 关闭条件

本债只有在下面结果可重复时才可关闭：

1. 对基准 fixture 连续 3 次运行能指出主要耗时属于首个 SSE、思考阶段、可见正文生成、请求固定开销、重试/缩块或供应商排队中的哪一类，且有指标证据。
2. 240 行基准在目标连接上不再出现隐式 Provider 重发；失败请求数、重试数和缩块数可从结果指标核对。
3. 选定的块大小/提示压缩/连接参数在 5、10、20、50 行对比中有明确的 p50/p95 改善，并且 240 行严格逐行覆盖、检查点恢复和资源约束没有回归。
4. 以当前旧基线为参照，至少达到“240 行任务 p50 不超过 2 分钟、p95 不超过 4 分钟”或由新的真实服务基线替代并记录原因；不能只凭一次成功运行关闭。
5. 仍保留首段和持续接收 UI；关闭性能债不等于删除流式活动 telemetry。

## 明确不做

- 不把六位数最大输出硬编码成所有模型的统一值。
- 不因为单块慢就放宽 `source_id`、指纹、事件证据、资源 allowlist 或原文覆盖。
- 不用 context length 估算 max output。
- 不在每次生成前联网抓官方网页。
- 不以“界面已经有字符滚动”作为总耗时已解决的证据。
