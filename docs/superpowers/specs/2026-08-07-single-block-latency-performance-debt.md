# 单场景块生成延迟性能债记录

状态：`OPEN`
建立日期：2026-08-07
责任边界：审查草稿 Annotation Agent 的单次模型请求与单块端到端耗时

## 为什么单独记录

本轮先处理确定性较高、可以直接减少失败和浪费的问题：

- `state_delta` 可选字段返回 `null` 时归一化为“不更新”；
- Provider 不再因内容 schema 错误静默重发完整请求；
- 容量错误、协议错误和连接错误分开处理；
- 容量成功缩块后，当前任务记住安全块大小；
- Provider 输出真实流式活动，Job/UI 显示等待首段、持续接收、重试和缩块；
- 记录实际模型、请求、重试、缩块、输入/输出和缓存报告。

这些改动可以让用户知道“现在在等什么”，也可以阻止已经确认的无效重试，但它们不能证明模型本身会更快完成一个场景块。尤其是把 `max_tokens` 从五位数改成六位数只改变截断上限，不等于提高生成吞吐，也可能扩大单次异常输出的成本上界。

因此本文件不允许被标记为“已由流式输出解决”。流式输出主要改善感知延迟；单块总耗时必须另行测量、定位和验收。

## 已知证据

以下数据来自近期真实运行记录，作为后续对比基线；没有 API Key、Authorization 或原始提示词写入本文件：

| 运行 | 原文行数 | 模型 | 总耗时 | 完成块 | 缩块块数 | 备注 |
|---|---:|---|---:|---:|---:|---|
| Gemini 基线 A | 240 | Gemini | 8.4 分钟 | 12 | 0 | 没有发生缩块 |
| Gemini 基线 B | 240 | Gemini | 11.9 分钟 | 12 | 0 | 没有发生缩块 |
| DeepSeek 慢运行 | 266 | `deepseek-v4-flash` | 约 59 分钟 | 18 | 10 | 多个块经历容量/协议失败后缩小 |
| 失败运行 | 101 | `deepseek-v4-flash` | 至少 14.6 分钟 | 7 个中的 5 个完成 | 5 | 最终 `state_delta.bgfx=null` 触发失败链 |

一次供应商用量截图包含 189,114 input tokens，其中 130,432 cached、58,682 uncached，约 69% input cache hit；output 106,711 tokens。结论是：缓存并非完全失效，失败响应、隐式兼容重发、重复纠正和缩块才是更直接的浪费证据。

## 当前根因假设

按可证伪性和预计影响排序：

1. **隐藏的 Provider 重发。** `OpenAIProvider._complete()` 当前在严格格式响应的内容/schema 解析失败时切到兼容模式，可能在 Agent 看见错误前已经完整再请求一次。可靠性计划会移除这个隐藏重发；完成后必须重新测量单块耗时和请求数。
2. **每块输出量和结构化协议开销过大。** 一个块必须返回每行多个字段、指纹、状态增量、事件和可选 beats；output tokens/target 需要由新 telemetry 记录，不能再靠总账反推。
3. **模型首段等待或服务端排队慢。** 旧实现只有块开始和块结束事件，无法区分 TTFT、持续生成和连接空闲。流式 `waiting`/`receiving` 事件完成后才能验证。
4. **模型实际生成吞吐低。** 需要 `output_tokens / (elapsed - first_delta)`，而不是只看请求总时长；思考 token、隐藏 reasoning 或供应商计费字段也要单独记录（若接口提供）。
5. **输入前缀/缓存边界不稳定。** `static_system`、易变上下文、场景窗口和重试提示的排列可能让缓存前缀失效；缓存命中率必须按请求和模型报告，不能只看一次供应商截图。
6. **最大输出设置造成异常长尾。** `384000` 能避免错误的五位数上限截断，但模型正常输出不应自动增长到上限；需要记录 finish reason、实际 output tokens 和是否接近上限，确认它不是长尾来源。
7. **块目标大小不适配模型。** 当前目标/软上限/硬上限是静态配置；可靠性计划会先学习容量安全上限，但不假设更小块一定更快，因为更小块会增加请求次数和重复上下文。

## 后续调查计划

这不是第一轮修复的执行内容；只有可靠性和上限计划完成并通过离线/小型真实冒烟后，才开始本节。

### 1. 建立固定基准

使用同一份 240 行、同一资源索引、同一提示版本、同一模型连接，分别运行 5、10、20、50 行目标块；每个配置至少重复 3 次。每次记录：

- request start、first delta、last delta、complete 时间；
- actual model、chunk size、input/output tokens、finish reason；
- retries、subdivisions、response-format fallback 次数；
- cache read/miss/reported、首段前是否有 reasoning 字段；
- output tokens/target、tokens/sec、请求成本（若供应商给出价格）。

实验只保存脱敏指标和请求 fingerprint，不保存提示词、脚本正文或响应正文。

### 2. 做四组可控对比

| 对比 | 变量 | 目的 |
|---|---|---|
| A | strict JSON schema vs 已明确兼容的 json_object | 证明是否仍存在格式协议额外延迟 |
| B | `max_tokens=16000/64000/384000`，其他不变 | 分离输出上限对 TTFT、finish reason 和长尾的影响 |
| C | 5/10/20/50 目标行 | 估算每块固定开销与每行边际开销 |
| D | Gemini 与 `deepseek-v4-flash` 同一 fixture | 区分供应商服务延迟和本地 Agent 开销 |

每组先跑离线 fake provider 验证计时器，再做受控真实请求；真实请求数量和预算必须先确认，避免为了测量再次造成大额消耗。

### 3. 按证据选择后续改动

- 若 TTFT 占主要耗时：研究连接复用、供应商队列、请求体大小和模型服务端路由；不先改标注语义。
- 若生成吞吐占主要耗时：减少无必要的输出字段/解释、检查 reasoning 配置，并比较结构化格式；保持逐行覆盖和身份校验。
- 若固定协议开销占主要耗时：压缩静态资源表和可变上下文，验证缓存前缀稳定性；不删除必要的状态/事件证据。
- 若缩块/重试占主要耗时：继续改错误分类和容量估算；不把所有错误都归为“输出太大”。
- 若 max token 只影响截断而不影响时延：保留自动能力匹配，不把它宣传为性能修复。

## 关闭条件

本债只有在下面结果可重复时才可关闭：

1. 对基准 fixture 连续 3 次运行能指出主要耗时属于 TTFT、生成吞吐、请求固定开销、重试/缩块或供应商排队中的哪一类，且有指标证据。
2. 240 行基准在目标连接上不再出现隐式 Provider 重发；失败请求数、重试数和缩块数可从结果指标核对。
3. 选定的块大小/提示压缩/连接参数在 5、10、20、50 行对比中有明确的 p50/p95 改善，并且 240 行严格逐行覆盖、检查点恢复和资源约束没有回归。
4. 以当前旧基线为参照，至少达到“240 行任务 p50 不超过 2 分钟、p95 不超过 4 分钟”或由新的真实服务基线替代并记录原因；不能只凭一次成功运行关闭。
5. 仍保留首段和持续接收 UI；关闭性能债不等于删除流式活动 telemetry。

## 明确不做

- 不把六位数最大输出硬编码成所有模型的统一值。
- 不因为单块慢就放宽 `source_id`、指纹、事件证据、资源 allowlist 或原文覆盖。
- 不用 context length 估算 max output。
- 不在每次生成前联网抓官方网页。
- 不以“界面已经有字符滚动”作为总耗时已解决的证据。
