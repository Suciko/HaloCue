# 有状态长剧本演出标注 Agent 设计

日期：2026-08-06

## 目标

将现有固定行数分块标注器升级为可扩展、可恢复、可审计的有状态标注 Agent。系统既要提高当前约 240 行、10 分钟剧本的跨块语义连续性，也要稳定处理 1 小时、数千行剧本，而不让单次模型请求随全文长度无限增长。

核心目标：

- 按自然场景和对话段落分块，不在固定的第 20 行机械切断语义。
- 当前块能够理解相关前文、必要后文、当前场景状态和跨场景剧情事件。
- 模型不依赖隐藏的连续聊天历史；全部长期状态由程序结构化保存。
- 每一目标行都有且只有一个响应，截断、漏行和重复行不能静默进入成品。
- 中断后从最近检查点继续，局部修改只重算受影响范围。
- 最终结果继续兼容现有草稿审查、资源合法性过滤、演出密度控制和 AA 编译流程。

## 非目标

- 不让模型改写、增删或润色原台词。
- 不修改 AA 的 EXE、配置、资源包、工作区文件或时间戳。
- 不以持续聊天会话作为唯一记忆来源。
- 首版不引入向量数据库、外部检索服务或多 Agent 编排框架。
- 不追求一次模型调用完成整篇标注。
- 不取消现有确定性补全、合法性过滤和人工草稿审查。

## 现状与问题

当前 `annotate.py` 默认按 `chunk_lines` 处理连续台词，并向每个新块传入最近 `context_lines` 行。前文包含已经采用的 `face`、`emo` 和 `act`，另有全章表情使用统计和可选的场景演出规划。

这已经避免了完全无上下文的独立请求，但仍有以下缺口：

- 固定行数可能在铺垫与回应、动作与结果、情绪上升与爆发之间切开。
- 当前块只看前文，不看紧邻后文，无法识别下一句对本句含义的消歧。
- 前文没有完整传递背景、持续背景效果、人物位置、近期音效等演出状态。
- 超过短期窗口的称呼、物品、承诺、笑点和伏笔无法可靠取回。
- 模型返回合法但不完整的 `lines` 数组时，当前流程可能接受并造成静默漏标。
- 任务中断后缺少逐块检查点；长剧本失败可能产生不必要的重复调用。

把 240 行甚至数千行一次性发送也不是稳健解法。现有 Schema 要求每行返回完整对象，输出会快速逼近 token 上限；全文越长，结构化输出截断、漏行和注意力稀释风险越高。

## 方案比较与选择

### 方案 A：连续聊天 Agent

每次请求继续上一轮模型会话，让服务商保留历史。实现表面简单，但模型或代理未必支持稳定会话；重试、换模型、进程重启和审计都很困难，也无法准确判断历史中哪些信息仍然有效。

### 方案 B：滚动文本摘要

每块完成后重写一段摘要并传给下一块。请求规模可控，但摘要反复压缩会逐渐丢失证据、伏笔和演出状态；自由文本也难以做局部失效和确定性校验。

### 方案 C：程序管理的分层记忆 Agent

原文、场景地图、结构化状态、剧情事件和逐块结果都由程序保存。模型每次读取有限的局部窗口和按需检索出的历史信息，并返回标注及状态增量。

本设计选择方案 C。它的实现成本略高，但最适合长剧本、断点恢复、局部重算和可验证输出。模型服务的提示词缓存只用于降低成本，不能替代程序状态。

## 总体流程

```text
读取并解析全文
  -> 构建确定性边界候选
  -> 全文预读：场景地图、故事摘要、初始事件
  -> 为场景生成自然语义块
  -> 逐块组装有限上下文
  -> 模型输出 lines + state_delta + memory_events
  -> 完整性、资源和状态校验
  -> 应用标注并提交检查点
  -> 更新场景状态与事件索引
  -> 全篇一致性复查并应用受限补丁
  -> 现有密度规范化、渲染和草稿审查
```

预读阶段负责建立导航信息，不做逐行演出标注。逐块阶段负责具体选择。复查阶段只返回补丁，不重新生成整篇。

## 组件边界

### `StoryPlanner`

输入完整的已解析剧本，输出故事摘要、场景地图和高价值初始事件。它可以调用模型，但必须以确定性边界候选为基础；模型失败时允许退回规则划分。

### `SemanticChunker`

根据场景地图、标题、`---`、地点或时间变化、旁白转换、完整对话轮次和长度约束生成目标块。它不调用模型，也不保存状态。

### `AnnotationMemoryStore`

保存版本化任务状态、场景状态、事件、块结果和输入指纹。提供原子检查点、恢复和失效范围计算，不负责语义判断。

### `ContextAssembler`

为一个目标块选择短期前后文、全局摘要、场景摘要、当前演出状态、密度统计和相关事件。它必须遵守输入预算，不能随着全文长度线性增长。

### `ChunkAnnotator`

调用现有模型 Provider，要求结构化返回逐行标注、状态增量和记忆事件。它不直接写最终文件。

### `AnnotationValidator`

校验行覆盖、原文身份、字段合法性、状态权限和事件证据。校验失败时给出可重试错误，不部分提交一个无效块。

### `ConsistencyReviewer`

在全篇初次标注完成后检查跨块和跨场景异常，只返回带证据的有限修正补丁。现有确定性密度与效果生命周期规则仍是最终守卫。

这些组件应保持独立接口，避免继续扩大 `annotate.py` 的职责。`annotate.py` 只保留顶层编排和对外兼容入口。

## 场景划分与语义分块

### 场景边界优先级

1. 明确章节标题、场景标题和 `---`。
2. 已确认的场景规划边界。
3. 旁白明确说明地点或时间变化。
4. 出场人物组合发生显著变化，并伴随叙事过渡。
5. 达到长度上限后，选择最近的完整对话轮次或旁白收束点。

模型不得用纯语义判断覆盖明确的用户分隔符。

### 块大小

- 目标长度：20 至 40 条待标注台词。
- 软上限：40 条；若继续几行即可闭合对话，可延长。
- 硬上限：60 条。
- 自动重试缩小档位：20 条、10 条、5 条。
- 场景少于硬上限时优先一次完成整个场景。

块身份由剧本指纹、场景 ID、目标源行 ID 列表和分块算法版本共同确定，不依赖易变化的数组位置。

## 每次请求的上下文

每个块最多包含以下信息：

1. 当前目标块，约 20 至 40 行。
2. 最多 15 条已标注前文，包含原文和已采用演出。
3. 最多 10 条未标注后文，只用于消歧，明确禁止输出标注。
4. 一份稳定的全局故事摘要。
5. 当前场景摘要和场景目标。
6. 当前演出状态。
7. 最多若干条与本块相关的历史事件。
8. 全章及近期演出密度统计。
9. 已确认的背景、音效等素材使用规划。

上下文使用明确的 `TARGET`、`PAST_CONTEXT` 和 `FUTURE_CONTEXT` 边界。Schema 只允许 `lines` 引用 `TARGET` 的稳定行 ID，避免模型给后文提前标注。

若输入接近预算，裁剪顺序为：低重要度历史事件、较远前文、较远后文、场景说明细节。当前目标块、合法资源约束、当前演出状态和高重要度未回收事件不得裁掉。

## 分层记忆模型

### 全局故事记忆

保存故事主题、人物关系、全局情绪方向和仍未回收的重要线索。它应短小稳定，不在每个块后重写整份摘要。

### 场景记忆

每个场景保存地点、时间、人物、场景目的、初始情绪和场景摘要。场景完成后写入最终摘要；未完成场景只更新可验证的增量。

### 演出状态

保存会影响后续行的当前状态：

- 当前背景和地点卡状态。
- 持续背景效果。
- 当前可见人物及已知位置。
- 每个角色最后采用的表情。
- 近期气泡、动作、音效和重效果。
- 现有密度控制需要的冷却信息。

瞬时效果不应错误进入长期状态。场景切换时，根据字段生命周期执行继承或重置，而不是清空全部记忆。

### 剧情事件记忆

保存需要跨窗口取回的事实，例如：

- 特殊称呼第一次出现及人物反应。
- 约定、承诺、误会和关系变化。
- 重要物品的获得、传递和使用。
- 笑点、伏笔及回收状态。
- 会影响后续演出的已发生事件。

每条事件至少包含：

```json
{
  "id": "event-0007",
  "kind": "relationship_callback",
  "participants": ["凯伊", "老师"],
  "keywords": ["凯伊酱", "称呼"],
  "summary": "老师称凯伊为凯伊酱，凯伊强烈否认",
  "source_ids": ["line-38", "line-40"],
  "evidence": "很适合你啊，凯伊酱。 / 才不是凯伊酱好吗！",
  "importance": 0.9,
  "status": "open"
}
```

事件必须有有效源行和证据。模型不能把推测直接升级为事实。关系类推断只能作为低置信度解释保存，不得覆盖原文事实。

### 短期窗口

短期窗口不是持久摘要，而是从原文、已完成标注和当前块位置即时构建。它负责连续对话、代词和紧邻情绪变化。

## 事件检索

首版使用本地结构化检索，不引入向量数据库：

- 人物、地点、物品和特殊称呼精确匹配。
- 当前块关键词与事件关键词匹配。
- 同场景或相邻场景加权。
- 未回收事件和高重要度事件优先。
- 近期事件给予适度加权，但不能压过明确的远期伏笔。

每块只注入少量最高相关事件，并保留源行号。全文达到数千行时，检索成本增长，但单次模型上下文保持近似恒定。

## 模型输出协议

逐块响应包含三个顶层字段：

```json
{
  "lines": [],
  "state_delta": {},
  "memory_events": []
}
```

### `lines`

每一个目标源行 ID 必须出现一次。字段继续覆盖现有 `face`、`emo`、`act`、`fx`、`se`、`bg`、`bg_request`、`place`、`shake`、`bgfx`、`trans`、`move` 和 `shot`。

响应不再依赖块内数字下标作为唯一身份。每项携带稳定 `source_id`，程序同时验证该 ID 的原文指纹。这样即使长台词被拆分，也能避免错位应用。

### `state_delta`

只描述本块内实际发生的持久状态变化。模型不能直接提交完整状态，也不能删除未授权字段。程序按字段白名单、人物可见性、资源约束和生命周期合并增量。

### `memory_events`

只记录可能影响后续理解的高价值事件。每项必须引用本块或可见上下文中的源行；程序去重并限制数量。普通表情变化、每句对话和一次性动作不进入事件记忆。

## 校验与事务提交

一个块只有通过全部校验后才能提交：

- `lines` 集合与目标源行 ID 集合完全相等。
- 没有重复、未知或属于后文的源行 ID。
- 原文指纹与请求时一致。
- 所有演出值通过现有资源 allowlist 和字段约束。
- `state_delta` 只修改允许的持久字段。
- 人物状态只引用有效演员和当前可见人物。
- 事件引用存在的源行并带有证据。
- 响应未因 token 上限截断。

模型输出中的单个非法演出字段可以沿用现有机制丢弃并产生提议诊断；行覆盖、身份或状态结构错误属于整块错误，不能部分提交。

每次成功提交原子写入：块结果、更新后的状态、事件索引、进度和诊断。文件写入失败时保留上一检查点。

## 重试和降级

重试顺序：

1. 对同一块做一次格式纠错重试，附上明确缺失或重复 ID。
2. 若输出截断或结构仍不完整，将块缩小到下一档。
3. 若某个最小块仍连续失败，停止任务并保留此前检查点。

全文预读失败时，退回确定性场景边界和最小全局摘要。事件检索异常时，退回短期窗口、场景摘要和演出状态。全篇复查失败时仍保留逐块标注结果，并显示复查未完成的诊断。

不允许因为一个块失败而删除此前成功结果或从头重跑全文。

## 缓存与断点恢复

### 模型提示词缓存

现有静态规则和资源表继续作为稳定提示词前缀，使用服务商支持的缓存能力。它只优化重复输入成本，不承担业务状态。

### 本地任务检查点

检查点至少保存：

- 任务 Schema 版本。
- 剧本、演员表、资源表和使用规划指纹。
- 提示词、Schema、分块器和记忆算法版本。
- 模型身份及影响语义的参数。
- 场景地图和全局记忆。
- 已完成块结果及逐块输入指纹。
- 当前演出状态和事件索引。
- 待处理块、重试次数和诊断。

API 密钥、完整请求头和不必要的本机绝对路径不得写入检查点。

### 缓存失效

- 剧本完全相同：复用全部已完成结果。
- 剧本局部变化：重新解析场景，从首个受影响场景开始重算；更早场景继续复用。
- 演员表变化：从首次出现受影响角色的场景开始重算。
- 背景、音效或表情资源变化：重算引用相关能力的块；无法精确判断时从相应场景开始。
- 提示词或输出 Schema 变化：所有模型标注块失效，但预读结果可在兼容时复用。
- 分块算法变化：场景地图可复用，块结果按新边界重新计算。

局部失效后的起始状态由最近有效场景检查点恢复，不能把后续旧状态继续拼接到新结果上。

## 全篇一致性复查

逐块完成后执行两层复查。

### 确定性复查

检查行覆盖、场景背景、持续效果生命周期、气泡和动作冷却、重效果密度、重复音效以及资源合法性。现有 `normalize_direction_density`、背景效果重置和性能规则继续作为最终守卫。

### 模型语义复查

按场景或相邻场景对摘要和关键标注进行复查，重点查找：

- 块边界两侧的表情或情绪突变。
- 伏笔、特殊称呼和关系回调与前文冲突。
- 场景转场遗漏或重复。
- 同一连续动作被反复配音效。
- 模型因只看局部而误判的关键反应。

模型只能返回带 `source_id`、原值、新值和理由的补丁。补丁通过相同资源与身份校验后才应用；不得重新生成未发现问题的行。

## 长剧本伸缩性

记忆组织为三层：作品、场景、块。数千行剧本会增加场景数、块数和调用次数，但不会把全部历史重复放入每次请求。

目标性质：

- 单次请求输入主要受块大小和固定记忆预算控制，与全文行数近似解耦。
- 单次结构化输出最多覆盖 60 行，正常覆盖 20 至 40 行。
- 已完成块立即落盘，任务运行时间增加不会放大丢失范围。
- 场景完成后生成稳定摘要，后续不反复压缩早期原文。
- 所有长期记忆保留源行证据，可随时回查原文。

## 与现有系统集成

- `annotate_script(options, provider_instance=None)` 保持现有调用方式和返回字段。
- 默认启用有状态编排；保留一个兼容开关，便于回归比较旧分块器，但不在普通 UI 暴露复杂设置。
- 现有 `filter_annotation_row`、proposal、确定性演出补全、密度规范化和渲染逻辑继续复用。
- 现有预检 `usage_chain` 作为场景规划输入，不由新 Agent 重复替换。
- 草稿仍在全部目标块成功并完成必要规范化后创建。
- 后台任务进度改为场景、块和复查阶段，继续向现有日志和 Job 状态报告。

## 用户体验

普通用户不需要理解 Agent、缓存或记忆参数。界面只显示有意义的阶段：

- 正在分析场景。
- 正在标注第 N/M 个场景。
- 正在检查全文一致性。
- 标注已暂停，可继续。

恢复任务时显示从上次进度继续。若源文件变化导致部分重算，应说明从哪个场景重新处理，不展示内部哈希或 Schema 版本。

## 数据安全与边界

- 只将标注所需的剧本文本、演员和资源语义发送给用户选择的模型服务。
- 本地记忆与检查点保存在现有项目数据范围内，沿用原子写入和公开字段清理规则。
- 错误日志不得记录 API 密钥或授权头。
- 模型生成的记忆不获得文件系统、AA 安装目录或外部服务操作权限。

## 测试设计

### 单元测试

- 场景分隔符、地点变化、完整对话轮次和硬上限产生预期边界。
- 当前块包含前 15 行、后 10 行，且后文不可成为目标行。
- 事件检索按人物、称呼、物品、未回收状态和重要度排序。
- `state_delta` 只能更新授权字段，瞬时效果不会进入持久状态。
- 缺行、重复行、未知 ID、后文 ID 和原文指纹变化均拒绝整块提交。
- 单个非法素材字段继续生成诊断，不破坏其他合法行。
- 检查点原子保存，并能恢复到最后成功块。
- 不同类型输入变化产生预期的缓存失效范围。

### 集成测试

## 验收标准

1. 240 行样本中每一条待标注行都有且只有一个经过验证的模型响应。
2. 块边界能够看到必要的前后文，并保持背景、表情、效果和音效状态连续。
3. 跨场景称呼、物品和伏笔可以通过带证据的事件记忆取回。
4. 3000 行样本的单次请求和输出规模受固定预算约束。
5. 任意成功块后中断，重启能够从下一块继续。
6. 局部修改不会无条件重算此前不受影响的场景。
7. 模型预读、事件检索或语义复查失败时存在明确降级路径，不破坏已完成结果。
8. 最终产物兼容现有草稿审查和 AA 编译流程。

## 实施顺序建议

1. 先引入稳定源行 ID、语义分块器和严格行覆盖校验。
2. 再增加演出状态、逐块事务提交和断点恢复。
3. 增加场景预读、剧情事件及结构化检索。
4. 最后增加全篇语义复查、局部缓存失效和 UI 恢复提示。

这个顺序优先消除静默漏标和固定边界问题；即使后续高级记忆功能尚未完成，前两个阶段也能独立提高可靠性。
