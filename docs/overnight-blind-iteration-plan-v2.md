# 0.9x 十小时高效率盲测迭代方案

## 结论

“每改一次提示词就把三个完整场景全部跑完”适合最终验收，但不适合十小时探索。它的问题是：

- 一次候选改动成本太高；
- 失败要等到整段结束才发现；
- 很难区分 G1、G2、后端策略和模型本身的责任；
- Agent 容易在一个失败 request 上反复 repair，消耗时间并造成过拟合。

十小时任务采用两级循环：

`三场景快速锚点筛选 -> 通过后再跑三场景完整轮 -> 官方事后对照 -> 只改一个共同问题簇`

三个场景始终使用同一轮版本号，但快速筛选和完整轮是同一轮的两个阶段，不是三个场景各自独立升级。

## 固定身份与隔离

- 模型：`gpt-5.6-sol`
- 模式：`balanced`
- 起始共享轮次：`V4`
- campaign：`proactive-v4-20260820`
- 旧目录 `output/sol-shared-v4-blind-balanced/` 只作审计封存；新 campaign 不覆盖它
- 新运行指纹必须包含运行模式、模型身份、source_id 和当前运行时文件聚合 SHA256，不能复用旧 checkpoint
- 每个场景独立目录、source_id、请求、响应、checkpoint 和 model-audit
- 单模型请求进程串行执行，不能使用默认并行 worker
- 不设置硬字符预算，不覆盖模型最大输出 token
- 不读取官方答案、官方命令流、人工标注、旧 AAP 或旧模型结果作为模型输入

### 持续运行与回执恢复

使用 `tools/run_blind_round.py --watch` 启动十小时 watcher。watcher 仍按
`jobs.json` 的声明顺序串行运行；遇到 `response_needed` 时只等待外部真实 Sol
子 Agent 写入与 request fingerprint 对应的 response 文件，然后从 checkpoint
继续。watcher 不生成、改写或覆盖 response，也不把旧 fingerprint 的 response
当作新请求答案。每次重放仍保留 `attempt-N.raw.json`，并更新当前
`RUN-STATUS.json`。

运行时构造资源提示词时，演员顺序必须来自稳定的首次出现顺序并用角色名
做确定性 tie-break；禁止从 `set` 直接遍历。否则同一盲测窗口的静态 prompt
会在重放间改变，产生无法匹配外部 Sol 回执的新 fingerprint。这是运行一致性
要求，不是导演质量规则。

建议根目录：

`output/sol-shared-v4-proactive-blind-balanced/`

场景目录：`main-p03/`、`seia/`、`main-3-1-7/`

## 阶段 A：三场景快速锚点筛选

每次提示词候选先只跑小窗口，不立即跑完整剧本。三个场景必须都参加筛选，并统一标记为当前轮次，例如 `V4`。

每个场景选择 3～4 个短窗口，窗口只根据盲测台词和通用语义特征选择，不能查看官方解析后再挑窗口。建议覆盖：

1. 普通信息交换：验证模型不会为了积极而机械加戏；
2. 新事实击中听者：验证听者反应是否可见；
3. 问号、感叹号、省略号或汇报落点：验证 face/emo/act 阶段是否变化；
4. 发现、操作反馈、关系压力或镜头转换：验证静默拍、硬切和连续性。

窗口必须带足够的前后文，使模型可以读取上文刺激和下一句承接；不能把单句孤立送入模型。
窗口范围、通用语义类别和选择理由必须先写入冻结 spec，再生成请求。三个场景的候选输出全部封存完成之前，不能读取本轮对应的官方命令、解析或差异答案。

`V4` 没有同 runtime、同三场景的有效 current-best，因此阶段 A 只跑 candidate。自 `V5` 起才允许用上一轮保留结果做隔离 A/B；candidate 请求始终不能读取 baseline response。

快速筛选仍然保留完整链路：

`原始 AI JSON -> compact -> validate -> policy -> AAP trace -> model-audit`

筛选只看以下六项，不追求字段数量：

- 承受刺激的人是否正确；
- 有阶段变化时是否至少有一个自然的可见承载；
- 无对白 beat 是否确实在下一句前有独立信息价值；
- 镜头是否服务互动轴，而不是只跟随 speaker；
- 站位、槽位和镜头状态是否连续；
- 是否增加了没有证据的剧情事实。

快速筛选的硬门槛：

- 三个场景都能编译；
- 没有对白 Wait；
- 没有四人同镜；
- 没有非法资源、人物瞬移或错误 enter/exit；
- 目标问题在至少两个场景改善，第三个场景不能明显退化。

不通过门槛就丢弃该提示词候选，只保留产物和诊断，不进入完整轮。

### 小规模 A/B 对照

每个重要提示词假设，优先在同一组锚点上做一次 current-best 与 candidate 对照。两次请求彼此独立，candidate 请求不能读取 current-best 的原始响应；
current-best 结果只用于生成完成后的比较。这样可以区分“提示词改变带来的改善”和“模型随机波动”。如果网络或时间只允许一次调用，至少保留上一轮完整结果作为事后控制，并降低结论强度。

对照不以“谁的 face/emo/act 更多”为胜负，而以同一锚点的因果承接、阶段可读性、镜头关系、静默必要性和连续性为判断依据。两者相当时，优先保留更短、更少重复规则的提示词。

## 阶段 B：三场景完整轮

只有阶段 A 通过，才按串行顺序跑完整场景：

1. `main-p03`；
2. `seia`；
3. `main-3-1-7`。

三个场景使用同一个版本号。完整轮必须生成完整 AAP、model-audit、原始 JSON、官方事后差异报告和轮次清单。

完整轮的目的不是再次寻找大量新规则，而是确认快速筛选中的改善能否泛化到不同文本、不同关系结构和不同静默密度。

## 唯一积极导演规则

每个事件主动扫描：

1. 注意对象改变；
2. 预期被打破或新信息落地；
3. 回答前的犹豫、迟疑或压住情绪；
4. 可见身体意图；
5. 关系压力或距离改变；
6. 结果落地后的情绪余波。

有因果价值时默认让变化可读，优先在对白节点使用 `face / emo / act / fx / camera / sound`。
只有必须在下一句开口前被单独看见的反应或结果，才拆无对白 beat。普通信息交换没有阶段变化时保持即可。

不要求 AI 编排连续多节点的完整默剧。长无对白链不是默认职责、数量指标或失败门槛；只检查关键反应、操作结果或决定是否需要一个短促、因果明确的独立 beat。不得为了接近官方无对白节点数量而补拍。

演出推断可以积极，剧情事实推断必须严格：可以表现停顿、视线、屏息、克制反应、潜台词和有动机的硬切；不能凭空增加物件操作、入场、退场、事件结果、关系事实或时间流逝。

## 阶段 C：责任归因

每个失败必须归到一层，不能笼统写“AI 不行”：

- 原始 AI JSON 缺少因果或表演判断：提示词 / G1 / 模型问题；
- 原始 JSON 有，compact 没有：协议展开问题；
- compact 有，validate 没有：校验问题；
- validate 有，策略后没有：后端策略问题；
- 策略有，AAP 没有：编译问题；
- AAP 有但与官方差异仍大：演出判断或提示词问题，不是字段完整问题。

G2 repair 只能修协议或硬错误。AI 明确返回的审美字段不能被后端静默替换；省略字段保持旧值，明确空值才清除。

## 十小时安排

每个假设只修改一个问题簇，建议时间分配：

- 约 70% 时间用于快速锚点筛选；
- 约 30% 时间用于通过筛选后的完整三场景轮。

建议顺序：

- `V4`：验证积极导演规则能否解除 `emo=0 / act=0`、长期同脸和阶段停滞；
- `V5`：只处理听者反应、静默拍、发现和操作反馈；
- `V6`：只处理站位交换、关系镜头、硬切和连续性；
- 后续：只处理三个场景共同出现的问题。

不要每轮都重新设计整套提示词，也不要为了一个场景的改善写专属规则。

## 保留与停止

只有以下条件同时满足，才把候选作为下一轮基础：

- 快速锚点阶段三个场景均通过；
- 完整轮三个场景均编译成功；
- 没有字段静默丢失、人物瞬移、错误入退场、对白 Wait 或四人同镜；
- 至少两个场景的官方差异有可解释的缩小；
- 第三个场景没有明显退化。

连续两轮满足以上条件后停止提示词改动，保留最佳完整轮交给人工审查。

如果只有圣娅改善而主线退化，不保留候选，检查是否过拟合。

## 必须保存的产物

每一轮、每一阶段都保存：

- `ROUND-MANIFEST.json`
- `RUN-STATUS.json`
- 所有 request、response、`attempt-N.raw.json`
- compact、validate、policy、AAP trace
- 每个场景的 `.model-audit.json`
- 快速筛选报告
- 完整轮官方事后差异报告
- 保留/拒绝理由

阶段 A 还必须保存冻结锚点 spec、`sealed-inputs/`、输入 SHA256 和串行 `jobs.json`。这些输入一旦封存，内容变化必须新建 campaign 或明确的新候选目录，不能原位覆盖。

十小时结束时必须汇报：最佳共享版本、三个 AAP 路径、三个审计路径、官方差异、仍需人工审查的问题，以及哪些变化来自 AI 新生成、哪些只是后端修复。没有可复现的官方相似度计算器，就不要声称百分比。
