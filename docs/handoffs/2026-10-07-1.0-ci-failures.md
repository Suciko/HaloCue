## 同时发现并修复的读取竞争

`get_work` 原来没有显式读事务，多个 SELECT 可以把旧 work.version 与新卡片、候选、运行状态混在同一个响应里。Harness 还使用独立连接读取另一个版本。新增 `test_work_read_snapshot.py`：在 SELECT work 与 SELECT volumes 之间执行真实人物卡保存，验证响应与 harness 都保持旧快照、下一次响应才看到新版本与人物卡。

- `get_work` 与 `_assemble_work_review_pack` 使用显式读快照。
- WritingHarness 可借用当前连接；独立调用自行开启读快照。
- 已接受 blueprint 的读取也使用同一连接，避免读快照持锁期间嵌套连接与等待提交的 worker 互相阻塞。
- 这不是把 CI 不稳定项一律归因于快照。新的回归测试只证明此前确实可以混读，以及当前修复保持一致。

## 延后候选的状态与停止保护

自动整理方向、结构、章节细纲和 managed 资料候选，父运行均保持 running 到候选提交。内部 `_result_guard` 只由服务调用传入，HTTP JSON 不参与该参数：提交前复查父运行仍可提交、授权版本仍有效；候选与父 waiting_user/proposal_id 原子保存。

新增延迟规划用例覆盖：用户停止、授权版本变化、结构化输出校验失败和 provider 异常。停止/授权变化后不提交迟到候选；失败进入 failed，原有对话回复保留；不会留下永久 running。手动整理入口继续按原来的审查方式使用，不要求伪造父运行。

## 验证记录

维护者本机 Windows / Python 3.13.12 / Node 22.19.0 / Playwright Chromium，TEMP/TMP 与 pytest basetemp 使用独立、可写且有空间的 QA 目录。其他机器只需自身工具链与合成夹具，不依赖维护者盘符、研究目录、真实 API 密钥或游戏媒体。

1. 对两个 CI 日志提取的全部 18 个原始 nodeid，在未修复起点执行：**13 failed / 5 passed，89.85 秒**。失败与固定 CI 失败一致。
2. 固定项修复及相关静态/HTTP 检查：**162 passed，80.67 秒**。
3. 焦点、混读、late memory checkpoint 的回归测试先失败，再通过：**3 passed，9.35 秒**。焦点在原始真实 HTTP 回包时丢失；混读在真实跨版本写入时出现；checkpoint 在真实后处理入口被重开。
4. 第一轮相关综合验收：**268 passed，337.84 秒**，包括所有原始失败文件、发布/恢复/harness、Gateway、四个制作导航窗口组合、六个 AA 素材浏览器用例。
5. 后续发现的延迟细纲问题，在基线 `5d28cbe6` 的服务源码上同一新浏览器回归失败：候选生成中父状态为 waiting_user。修复后讨论/按需工具及延迟成功/停止/授权/失败用例：**28 passed，19.37 秒**。
6. 最终扩展验收：**386 passed，438.61 秒**；追加了 dispatcher、async、scene edit、conversation 与场景 harness，避免仅修复浏览器按钮而破坏运行和停止流程。所有原始失败均包含在此参数列表中（两个陈旧用例使用上述更准确的新名称）。
7. 全部改动 Python 文件逐项与基线 Ruff JSON 诊断比较：**无新增 lint 项**。service.py 仍有基线已存在的三个项（unused FakeWritingProvider import、unused version、unused skill_ready）；其余改动文件检查通过。章节浏览器的共享 pytest fixture 改用显式 re-export，删除无用的接收变量，保持实际第二场创建与断言。
8. `node --check services/halocue/writing/web/app.js`、`git diff --check` 通过。`ruff format --check` 检查的六文件中仅新增 read-snapshot 文件完全通过，五个既有文件仍要求格式化；没有对这些已有大文件进行整文件重排，不能宣称全文件格式检查通过。
