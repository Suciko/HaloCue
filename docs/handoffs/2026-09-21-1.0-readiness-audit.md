# 1.0 formal-user readiness audit — 2026-09-21

## Verdict
The integrated local workbench is usable for supervised internal alpha testing, but it is not yet a formal 1.0 release candidate. A practical estimate is roughly 70% of the way to a stable user-facing release: the main writing/AA navigation, model settings, saved-model picker, production background import and many UI contracts exist; release evidence and regression closure are not complete.

## Evidence collected
- Current branch: `codex/1.0-release-readiness-20260914`; worktree has extensive unrelated modified files, deleted historical plan files, scratch/temp directories and many untracked handoffs. No clean release commit/tag exists.
- Production regression: `python -X utf8 -m pytest services/halocue/production/tests -q` -> **428 passed** (2026-09-21).
- Combined selected writing/production regression -> **207 passed, 21 failed** (2026-09-21). Failures are concentrated in `services/halocue/writing/tests/test_http_api.py` static UI contracts. They include missing expected user-status markup, agent runtime markup, decision-card markers, production embed/navigation markers and writing-route contracts. Some tests may be stale after the redesign, but they cannot be ignored until each is classified as updated contract or regression.
- Live integrated service was restarted after testing: port `8928`, PID `10728`; `/api/v1/health` returned 200. Current provider is real `gemini-3.8-flash (openai)`, not simulation; dispatcher running; no queued reconciliation errors.
- Latest packaged acceptance evidence is from **2026-09-15**, before the subsequent 2026-09-19 model-picker/sidebar and current UI changes. It cannot serve as final evidence for the current tree.

## Release blockers
1. **Regression closure**: classify/fix/update the 21 writing UI contract failures; add browser smoke for the current integrated surface.
2. **Current-tree packaging**: rebuild public/private release from a clean accepted commit and rerun `verify_integrated_release.py` / `verify_release.py`; prior 2026-09-15 bundle is stale.
3. **Native AA acceptance**: prior readiness explicitly left authorized native playback pending: slot-zero teacher, consecutive/terminal selection, five portraits, CG, native compile and installation. Synthetic tests are not substitutes.
4. **Production resource completeness**: the 2026-09-19 import audit found 2,307 ready, 407 unresolved, 59 ambiguous out of 2,773 entries. Existing background import deliberately does not extract uncached official bundles; unresolved/ambiguous records need an explicit user-facing boundary or resolution workflow before claiming full library readiness.
5. **Real production handoff evidence**: docs still record missing/insufficient proof around asset-copy receipts in the current formal path, remote 429/504 behavior, provider cost receipts/cache policy and real AA persistent installation. These may be release-scope decisions, but must be declared rather than implied complete.
6. **Worktree/release governance**: split the large dirty tree into focused accepted changes, preserve or intentionally review deleted plans, then tag the exact accepted commit and run signed release workflow.

## Recommended order
P0: reconcile the 21 failing writing contracts; run browser smoke for writing -> freeze release -> AA production -> background selection -> review -> compile/install using authorized local AA resources.
P1: resolve or explicitly gate unresolved/ambiguous resource entries; verify current production handoff receipts and retry/failure paths.
P2: run the current-tree package verification, clean release review, version tag and signed workflow.

## User-facing conclusion
Current build can be used by the maintainer for supervised testing. Do not yet hand it to ordinary users as “1.0 stable”; the gap is primarily release verification and native AA acceptance, not another broad visual redesign.
