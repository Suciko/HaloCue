- This is a synthetic provider control, not a fresh 33-line performance generation, and it did not mutate the reviewed draft. It demonstrates that the configured route can report a cache hit for an identical repeat, not that different production chunks now have a guaranteed cache hit.

Manual hit calculation: `12,261 / (4,040 + 12,261) = 75.216244%` for the repeat. Weighted experiment rate: `12,261 / 32,602 = 37.608122%`. The compatible response counts cached tokens inside `prompt_tokens`; this provider's billing receipt uses `prompt_tokens` for ordinary input and a separate `cache_tokens`. Do not divide by 4,040 alone or add the cached count to the response's already-inclusive total.

Manual charge cross-check using only this receipt's factors: model factor 0.75, group factor 1, cached-input factor 0.1, output factor 6. Repeat charge is `0.75 * (4,040 + 12,261 * 0.1 + 5 * 6) = 3,972.075` quota units; actual rounded charge is 3,972. First charge is `0.75 * (16,301 + 5 * 6) = 12,248.25`, rounded to 12,248. Receipt conversion uses 500,000 quota units/USD. These are observed account factors, not general model pricing.

Charge inversion independently yields cached input: `C = (I + O * output_factor - quota / (model_factor * group_factor)) / (1 - cache_factor)`. The repeat gives approximately 12,261.11; the small residual follows quota rounding. Raw usage and provider billing agree with 12,261 cached tokens.
